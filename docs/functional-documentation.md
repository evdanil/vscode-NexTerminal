# Nexus Terminal Functional Documentation

## 1. Product Goal
Nexus Terminal provides one operational surface in VS Code for:
- SSH terminals
- SSH port-forwarding tunnels
- SFTP file management over SSH
- Serial connectivity through isolated sidecar IPC

## 2. Implemented Architecture

### 2.1 Core Components
- `NexusCore` (`src/core/nexusCore.ts`): state manager for servers, tunnel profiles, active sessions, active tunnels.
- `SilentAuthSshFactory` (`src/services/ssh/silentAuth.ts`): credential loop with `SecretStorage` and keyboard-interactive 2FA support.
- `Ssh2Connector` (`src/services/ssh/ssh2Connector.ts`): concrete SSH transport.
- `SshConnectionPool` (`src/services/ssh/sshConnectionPool.ts`): shared SSH connection manager for multiplexed terminals, tunnels, and SFTP.
- `TunnelManager` (`src/services/tunnel/tunnelManager.ts`): local TCP listeners + SSH forwarding.
- `SftpService` (`src/services/sftp/sftpService.ts`): shared SFTP operations layer backing the file explorer and `nexterm://` filesystem provider.
- `TunnelRegistrySync` (`src/services/tunnel/tunnelRegistrySync.ts`): cross-window tunnel ownership and visibility sync.
- `SerialSidecarManager` (`src/services/serial/serialSidecarManager.ts`): JSON-RPC sidecar client.
- `serialSidecarWorker` (`src/services/serial/serialSidecarWorker.ts`): isolated process runtime.
- `TelnetPty` (`src/services/telnet/telnetPty.ts`): raw telnet terminal transport.
- `TelnetNegotiator` (`src/services/telnet/telnetProtocol.ts`): pure RFC 854 IAC state machine (no `vscode`, no socket).

### 2.2 Isolation Model
- Interactive SSH terminals use `SshPty` shell channels. When SSH multiplexing is enabled, those channels can share a pooled underlying SSH connection; per-server disable and automatic standalone fallback are supported.
- Tunnels default to shared mode: all TCP clients reuse a single SSH connection. Isolated mode (one SSH connection per client) is available as a per-profile or global setting.
- SFTP reuses the shared SSH pool when connected to the same server.
- Serial code executes outside the extension host process.
- Telnet terminals run in-process on a plain `net.Socket`, like SSH — there is no native module to isolate.

## 3. Data Models
- `ServerConfig` and `TunnelProfile` defined in `src/models/config.ts`.
- `SerialProfile` defined in `src/models/config.ts` (`path`, `baudRate`, `dataBits`, `stopBits`, `parity`, `rtscts`, optional `group`, optional `mode`, optional `deviceHint`).
- `AuthProfile` defined in `src/models/config.ts` for reusable username/auth method templates linked to multiple servers.
- Persisted via `VscodeConfigRepository` into `globalState`.
- Password secrets persisted via VS Code `SecretStorage` using key pattern `password-${serverId}`.

## 4. User Workflows

### 4.1 Server Management
1. Run `Nexus: Add Server` (or use the unified `Nexus: Add Profile` form).
2. Fill host/auth details.
3. Server appears in **Connectivity Hub**.
4. Right-click server item to connect/disconnect/edit/remove/duplicate/rename.

#### 4.1.1 Profile Quick Actions
- `Nexus: Add Profile` opens the unified profile flow for SSH server or Serial profile creation.
- The tree-only `nexus.profile.actions` command opens the **Profile Actions** quick pick from a profile item. It is hidden from the Command Palette and exposed through the tree.
- Server profile actions include **Connect**, **Test Connection**, **Browse Files** when connected, **Connect and Run Script**, **Edit**, **Duplicate**, **Copy Connection Info**, and **Delete**.
- Serial profile actions include **Connect**, **Test Connection**, **Connect and Run Script**, **Edit**, **Duplicate**, **Copy Port Info**, and **Delete**.
- Local Shell profile actions include **Open Local Shell**, **Open and Run Script**, **Edit**, **Duplicate**, **Copy Shell Info**, and **Delete**. Local Shell profiles do not show a Test Connection action.
- The Local Shell VS Code profile dropdown lists only terminal profiles that expose an explicit executable path to extensions. For WSL, use a custom Local Shell profile with `wsl.exe` as the shell path and any distribution arguments as shell arguments.
- Folder actions use folder-specific labels for bulk operations: **Connect Folder Servers** and **Disconnect Folder Servers**.

#### 4.1.2 Connection Test Diagnostics
- Server profiles expose **Test Connection** (`nexus.server.testConnection`). It opens a progress notification, attempts an SSH connection with the same profile configuration, disposes the test connection on success, and shows `Connection test succeeded for <name>.`
- On SSH failure, the test classifies the connection error and shows a diagnostic title/detail pair with **Copy Details**. Copying details writes the formatted diagnostic text to the clipboard.
- Serial profiles expose **Test Connection** (`nexus.serial.testConnection`). Standard serial tests check whether the configured port path is currently available.
- Smart Follow serial tests also compare the saved path and saved hardware hint. Results distinguish saved-path availability, matching-device availability, and missing-device states. Failure prompts can offer **Scan Serial Ports**.

### 4.2 Silent Auth (Password mode)
1. Lookup in secret vault.
2. Attempt login.
3. On auth reject, delete stored secret.
4. Prompt user for new password and optional save.
5. Retry with new secret.

### 4.3 SSH Authentication
Supported authentication types:
- **Password** — stored in VS Code SecretStorage, auto-filled on reconnect.
- **Private key** — reads key file from disk, prompts for passphrase if encrypted.
- **SSH agent** — delegates to the system SSH agent via `SSH_AUTH_SOCK`.

All auth types support **keyboard-interactive 2FA**: `tryKeyboard` is enabled globally so servers can request verification codes after primary auth. When an `InputPromptFn` is provided (wired to `vscode.window.showInputBox` in production), the handler auto-fills password-like prompts and shows an input box for all other prompts (e.g., OTP codes).

### 4.4 SSH Terminal Session
1. Run `Nexus: Connect Server` (or context action).
2. A custom PTY terminal is created (`Nexus SSH: <server>`).
3. Terminal opens in an editor tab by default, or in the terminal panel when `nexus.terminal.openLocation` is set to `panel`.
4. Session appears in **Connectivity Hub**.
5. Unread output marks both the sidebar session node and the terminal tab title until the terminal regains focus.
6. Output/input logs are written under extension global storage logs.
7. Client errors raised after the connection is ready (keepalive timeout, protocol error) and every connection close are written to the **Nexus SSH** output channel, tagged with the server name, host, and ssh2's own `err.level`. Pre-ready errors are not logged there — they are returned to the connect flow, which handles auth retries and host-key prompts. The channel takes no configuration and stays inert until it is opened.

#### 4.4.1 SFTP File Explorer Operations
- **Browse Files** (`nexus.files.browse`) selects an active connected SSH profile as the SFTP target.
- SSH profiles can enable **Open File Explorer on first connection** in advanced options. After a normal **Connect**, Nexus starts SFTP and switches the single **File Explorer** view to that server when it is not already active there.
- Only one SSH profile can have this automatic File Explorer behavior enabled. Saving it on one profile clears it from any other profile.
- Automatic File Explorer opening does not run for jump-host use, tunnel starts, group Connect, or Connect and Run Script.
- The **File Explorer** view supports open, upload, download, delete, rename, new directory, new file, go to path, go home, copy remote path, refresh, and disconnect commands.
- Upload and download operations track summary counts for completed items, failed items, skipped items, conflicts, and cancellations. A skip is a deliberate refusal (symbolic link, unsafe name, destination exists); an item that was attempted and could not be transferred is counted as **failed** and is never folded into the skip count.
- Drag-and-drop uploads report `Upload completed`, `Upload finished with failures`, `Upload completed with skips`, or `Upload canceled` notifications with summary counts. A drop that yields no usable local file paths — the usual shape of a drag originating outside VS Code, which offers bytes but no `uri` — reports that nothing was uploaded instead of silently doing nothing.
- Recursive uploads skip symbolic links, unsafe entry names, and directories beyond the upload depth limit. A local path that cannot be read, and a remote stat/mkdir that errors, are reported per item and counted as failures rather than skips.
- Every upload and download is size-verified once it completes, against the size the transfer was planned with. A file whose remote (download) or local (upload) stat reports `0` cannot be size-planned — `/proc` entries and some appliances mis-report it, and ssh2 treats a planned size of `0` as "done" with no error — so it is read to EOF instead, bounded by `nexus.sftp.maxOpenFileSizeMB`. Past that bound the transfer stops with a message naming the limit and the setting.
- Editor saves and **New File** write through a mode-preserving path: an existing remote file keeps its own permissions, and a new file is created under the remote server's `umask`. The previous path chmod'd every file it opened for writing to `0666`.
- Local-side transfer IO uses `node:fs` rather than `vscode.workspace.fs`, because the latter launders VS Code's UNC restriction (`ERR_UNC_HOST_NOT_ALLOWED`, raised by `security.restrictUNCAccess`) into a `FileSystemError` with code `"Unknown"`. A blocked host is matched on `err.code`, collected once per operation, and offered a consent-gated remediation after the transfer finishes: an error message naming the host, then **Allow Host…** behind a modal that names both the host and `security.allowedUNCHosts` before anything is written to user settings. `security.restrictUNCAccess` is never modified, and declining at either step writes nothing. Because the extension host receives its allowlist only at spawn, the blocked path is re-probed after the write; **Reload Window** is offered only when it still fails.
- Downloads no longer open the local destination from inside ssh2's callback stack. That open ran on the `net.Socket` 'data' stack, so a synchronous throw from Node's path validation (UNC policy, embedded null byte, non-string path) unwound the protocol parser and destroyed the shared `ssh2.Client`, dropping every terminal multiplexed onto that server. The destination is now pre-probed with `lstat` on Nexus's own stack — nothing is created or truncated, and creation/truncation stay with ssh2's own open after the remote file is known to be readable. Fatal SFTP channel errors are likewise contained: the SFTP session is torn down and reported, and terminal sessions leasing the same connection are unaffected.
- Transfers whose local side is a Windows network path (`\\server\share`, `//server/share`, `\\?\UNC\…`) use 8 concurrent 32 KB operations instead of ssh2's default 64, which otherwise queues far more parallel `fs` work than libuv's 4-thread pool can serve and stalls the extension host whenever the share does. Mapped drive letters are indistinguishable from local disks without win32 API calls and keep the default profile.
- Blocked UNC hosts, per-transfer byte counts, drag-drop upload outcomes, and SFTP session teardowns are written to the **Nexus SSH** output channel (see 4.4).
- Recursive deletes are constrained by `nexus.sftp.deleteDepthLimit` and `nexus.sftp.deleteOperationLimit`.
- Directory listings use the SFTP cache and remote watch settings. Manual refresh invalidates cached entries for the active target.
- **Save as Root**: SFTP writes as the logged-in SSH user, so a root-owned file normally fails to save. If a plain save is denied, Nexus offers to retry over `sudo` (declining suppresses the offer for that file until it's closed or Edit as Root is chosen); a file with no write bits at all (`0444`) can be marked editable up front via **Edit as Root (sudo)** (`nexus.files.editAsRoot`) in the File Explorer context menu or the command palette (when a `nexterm://` file is the active editor), since VS Code blocks editing such a file before any save is attempted. This covers writes only — elevated reads are not supported, so a file the SSH user can't even read still fails to open. The content is staged to a temporary path over SFTP, then moved into place with `sudo` on an SSH exec channel — the write goes through the target's existing inode when it already exists, so owner, mode, ACLs, and hard links are preserved; a new file, or one recreated because it vanished remotely between open and save, is created using the mode last observed for it (`644` if none was ever observed) — read/write bits only; a recreated file never comes back with execute or setuid/setgid/sticky bits, which can be narrowed but never restored. The sudo password (asked only when the account actually needs one) is piped to the exec channel's stdin and is never written to disk, secret storage, or a log; `nexus.sftp.sudo.rememberPasswordForSession` optionally keeps it in memory until that server disconnects or the window closes — though even with it off, the remote host's own sudo credential timestamp can let consecutive saves skip the prompt. A staged write the server refuses outright (no space left, an over-quota home directory, an appliance rejecting the path) fails the save rather than being installed over the target — ssh2's SFTP write stream emits the same single `close` for a rejected write as for a completed one, so success is gated on the per-write acknowledgement plus a clean close, not on `close` alone. The write is **not atomic** — a disk-full condition or a dropped connection mid-write can leave the target partially written with no backup, so a failed elevated save should be retried rather than abandoned. Sudoers policies requiring a TTY (`requiretty`) are unsupported and reported as such, along with a workaround. The whole feature is gated by `nexus.sftp.sudo.enabled`. Elevation depends on the SSH account actually having sudo rights on the remote host — the password prompt normally asks for the account's own login password, not root's. Knowing the root password doesn't help if the account isn't in sudoers, since sudo authenticates the invoking user rather than accepting root's password in its place; the practical workaround is a second Nexus server profile that logs in as root over SSH (only possible if the host permits root SSH login) and edits the file directly. Elevating with the root password via `su` instead of `sudo` is not supported and isn't planned: `su` reads its password from `/dev/tty` rather than stdin, and Nexus has no PTY channel to drive that prompt. Hosts that set `Defaults rootpw` (or `targetpw`) make sudo want root's password instead of the account's own — the retry prompt shown after a rejected password notes this possibility.

#### 4.4.2 Directory Sync (Follow Terminal Directory)
Keeps the File Explorer pointed at whichever SSH terminal is focused, tracking that terminal's current directory instead of sitting wherever it was last navigated. Two parts: continuous sync for shells that announce their own directory, and a manual, on-demand sync for everything else. Neither part writes anything to the terminal/pty channel in this release — the feature only reads what the shell already sends, or asks the user for a path directly.

- **Turning it on/off** — a three-way toggle occupies the leftmost slot (`navigation@1`) of the File Explorer title bar, guaranteed inline (it never falls into the `...` overflow), and the same three actions are mirrored on the right-click context menu of the `.` row (the row showing the current directory). There is no setting for this: the on/off state lives in `globalState`, never in `settings.json`, so turning it off never requires opening Settings.
  - **Follow Terminal Directory** (`nexus.files.followTerminal`, `$(link)`) — shown when off; turns following on, clears any pause, and — if the focused SSH session already has an applicable tracked directory and the explorer is idle and visible — immediately re-roots to it rather than waiting for the next reported `cd` or focus change.
  - **Stop Following Terminal Directory** (`nexus.files.unfollowTerminal`, `$(circle-slash)`) — shown while following and not paused; turns following off entirely.
  - **Resume Following Terminal Directory** (`nexus.files.resumeFollowTerminal`, `$(pinned)`) — shown only while paused (state 5 below); clears the pause and immediately re-roots to the terminal's last known directory.
  - Turning **Follow Terminal Directory** on for a focused SSH session that has never reported a directory (state 3) immediately shows an actionable notice — `"<server>" hasn't reported its directory yet...` — with **Show Me How** (writes the rc one-liner to the "Nexus Directory Sync" output channel and opens it) and **Go to Terminal Directory** (jumps there once, manually) as the two responses. Fires at most once per server per window, tracked in memory only, so it reappears after a reload or if a different server hits the same state.
- **Go to Terminal Directory** (`nexus.files.syncFromTerminal`) — a one-shot sync independent of the toggle, and the only new command Phase 1 puts in the overflow group (`1_sync@1`) rather than inline, since it is a secondary action next to the toggle. Also reachable from the `.` row context menu and from the right-click menu on any Nexus terminal tab (docked in the panel, or opened as an editor tab — both are covered). Resolution ladder: (1) the last directory the focused terminal reported, if not stale; (2) failing that, a heuristic candidate read from the terminal's own visible prompt text; (3) whichever candidate steps 1–2 produced is validated with `realpath` plus a directory check before the explorer re-roots; (4) if nothing validated, the Go to Path box opens prefilled with the best candidate found (or the current root) instead of dead-ending; (5) if that also yields nothing, a one-time-per-session notice explains the host never reported a directory. A successful sync (automatic or via the prefilled box) also clears any pause, since this command moves the explorer *toward* the terminal rather than away from it.
- **Continuous coverage** — genuinely continuous, not a poll, for any shell that emits the `OSC 7` "here is my directory" escape sequence before its prompt: `fish` (≥ 3.x) does this unconditionally, and prompt frameworks such as `starship` do too. Plain bash and zsh don't by default; one added snippet each makes them:
  ```bash
  # ~/.bashrc — let Nexus follow this shell's directory
  PROMPT_COMMAND='printf "\033]7;file://%s%s\033\\" "$HOSTNAME" "$PWD"'"${PROMPT_COMMAND:+; $PROMPT_COMMAND}"
  ```
  ```zsh
  # ~/.zshrc — let Nexus follow this shell's directory
  __nexus_osc7() { printf '\033]7;file://%s%s\033\\' "${HOST}" "$PWD"; }
  precmd_functions+=(__nexus_osc7)
  ```
  Once added, that shell reports its directory on every prompt from then on. (zsh sets `$HOST` automatically; `$HOSTNAME` is frequently unset there, unlike in bash.)
- **Non-POSIX devices** — Cisco IOS, Juniper, FortiOS, out-of-band console servers, and similar gear never emit `OSC 7` and have no prompt Nexus's heuristic can parse. Nothing breaks: following simply never activates for that session, silently — no periodic retries, no repeated errors, no probing traffic sent to the device. The one exception is **Go to Terminal Directory**: the first time it runs against such a session and finds nothing to sync, Nexus shows one informational message for that session only (`"<server>" didn't report a directory, so Nexus can't follow it. Directory sync is off for this session.`) and stays silent for the remainder of that session.
- **Manual navigation and pausing** — using Go to Path, Go Home, or the `..` row pauses following (state 5, "Pinned") instead of silently overriding your navigation on the next reported directory change. Expanding a subdirectory is not navigation and never pauses anything. **Resume Following Terminal Directory** (or the toggle) clears the pause and jumps to the terminal's current directory; the pause also clears automatically on an explorer server change or a session teardown.
- **The seven states**, rendered in the File Explorer view's title-bar description line (and, for the one abnormal case, as a banner pushed above the tree):

  | # | State | When it happens | What to do |
  |---|---|---|---|
  | 1 | Off | Following is turned off. | Turn it on if you want it. |
  | 2 | Following | On; the focused terminal's server matches the explorer's active server; its last reported directory is 60 seconds old or newer. | Nothing — this is the normal working state. |
  | 3 | Shell not reporting a directory | On and matched, but the host has never reported a directory (no `OSC 7`, and the prompt heuristic never matched). | Run **Go to Terminal Directory** once for a one-time diagnosis, or add the rc hook above if it's a bash/zsh host. Turning Follow on for a host in this state also raises an actionable notice immediately (see below), rather than leaving you to notice the quiet title-bar text on your own. |
  | 4 | Stale | On and matched, but more than 60 seconds have passed with terminal output since the last report — typically `sudo -i`, `su`, `tmux`, or a nested `ssh` swallowing the hook. | Nexus does not re-root automatically on stale data; run **Go to Terminal Directory** if you want to catch up manually. |
  | 5 | Pinned (paused) | Following was on, but you navigated manually (Go to Path / Go Home / `..`). | Click **Resume Following Terminal Directory** to jump back to the terminal's directory and clear the pause. |
  | 6 | Following another server | The focused terminal is connected to a different server than the one the File Explorer is currently showing. | Switch focus to a terminal on the explorer's server, or point the explorer at the terminal's server instead — Nexus never auto-switches the explorer's active server on a focus change. |
  | 7 | Rate-limited off | The terminal reported directory changes faster than Nexus could safely apply them; following was turned off automatically for that session as a burst-protection measure. | Click **Follow Terminal Directory** to turn it back on. |

#### 4.4.4 Telnet Terminal Session

Telnet is a per-server **protocol** choice, not a separate profile type: one server record, a `Protocol` select on the add/edit form with **SSH** (default) and **Telnet**. `ServerConfig.protocol` is optional and absent means SSH, so nothing changes for existing servers and there is no migration.

1. Set **Protocol** to *Telnet* on a server profile. The SSH-only controls — Username, Authentication, Private Key File, Auth Profile, Alternate host, Proxy/Jump Host, connection multiplexing, legacy algorithms, and the automatic File Explorer — hide themselves, because telnet reads none of them. Switching **Protocol** also moves **Port** between 22 and 23, but only while that port is still the automatic default — the value is auto-derived only if it matched the default for the protocol the form *opened* on, and it stops being auto the moment you type in the field. A port you typed is left alone, so an SSH server hand-set to 23 survives a protocol round-trip instead of being rewritten to 22.
2. Run `Nexus: Connect Server`. The connect path branches **before** any credential handling: `SilentAuthSshFactory` is never reached, so there is no password prompt and no vault access.
3. A custom PTY terminal is created (`Nexus Telnet: <server>`), registered with the `TerminalRegistry` and with `NexusCore` as an ordinary `ActiveSession`. Highlighting, the capture buffer, Reset / Clear Scrollback / Copy All, macros and scripts all behave exactly as they do for SSH.
4. Log in at the device's own prompt, in the terminal. **Telnet is cleartext and has no protocol-level authentication** — that is the protocol, not a limitation of this client. The intended targets are console servers and lab gear on a trusted management network.

**Protocol handling.** A separately tested IAC state machine parses negotiation out of the byte stream: it accepts the server's `WILL ECHO` / `WILL SGA`, agrees to `DO SGA`, answers TERMINAL-TYPE with `xterm-256color`, and reports the window size through NAWS on every resize (0xFF dimension bytes escaped). Everything else is refused, and each option is answered only when the answer changes — two polite implementations never loop. `IAC IAC` is unescaped in both directions, `CR NUL` collapses to `CR`, `CR LF` passes through, and outgoing keystrokes get the NVT `CR LF` newline most network-OS consoles expect. Binary mode is deliberately not negotiated: non-IAC bytes already pass through untouched, so UTF-8 works without it.

**Lifecycle.** A connect that does not complete within 10 seconds, a refused connection, or a socket error before the session is up all report `[Nexus Telnet] Connection failed: …` in the terminal and leave the tab open on a press-any-key notice — no session is registered. A remote close reports `Remote host closed the connection.` and unregisters the session.

**What telnet does not do.** SFTP browsing, port forwarding, jump hosts, SSH key deployment, Test Connection, directory sync and connection multiplexing are all SSH machinery. Each refuses rather than failing later inside an SSH handshake, and the refusals differ by kind:

- **Refused out loud, naming the feature and the server** — File browsing (SFTP), Port forwarding (including dragging a tunnel profile onto the server), Test Connection, Deploy SSH Key.
- **Not offered, then refused anyway** — a telnet server is left out of the **Jump Host** and **IPMI Gateway** pickers, and the SSH connect path refuses a stored jump-host id that resolves to one *before any credential is read or requested*. The second half is load-bearing: a server can be switched to Telnet long after another server named it, and no picker can retract a choice already saved.
- **Silently skipped** — Directory sync (Follow Terminal Directory). If the File Explorer is rooted on a server that is later switched to Telnet, the sync stops instead of sending path text extracted from the device's own output to an SFTP call. Silent by design: this path runs on terminal output, so a notification would repeat for a state the user never asked about.
- **Never engaged** — connection multiplexing and the SSH connection pool are only reached from the SSH connect path, which a telnet server branches away from before any of it.

**Forward/backward compatibility.** `protocol` is additive and optional, so an older build round-trips a telnet record's *other* fields untouched — but it does not understand the field itself, and will connect such a server over SSH. A configuration exported here and imported by a pre-2.8.188 build therefore loses the protocol (and, with it, the meaning of a blank username). Nothing on this side can prevent that; the field does not exist in the older schema.

**Inventory.** `InventoryEndpointKind` includes `"telnet"`. A device whose only usable endpoint is telnet syncs to a telnet server on port 23 by default; a device offering **both** ssh and telnet maps to SSH, whatever order the endpoints are listed in. The `ServerOrigin.syncedProtocol` stamp records what the sync wrote, so a protocol you change by hand is never overwritten by a later sync, while a device that genuinely changes transport is still followed.

**Protocol and address are decided together (#81).** The endpoint is selected for the protocol the record will ACTUALLY end up with, not for the device's preferred endpoint. Where the sync owns the protocol that is the primary endpoint and nothing changes; where the USER owns it — a hand-flip the stamp protects — the address must come from an endpoint of THAT transport, since otherwise a hand-set telnet server on a dual-stack device was rewritten to the ssh endpoint's host and port 22, i.e. a telnet profile aimed at the ssh port. **Where the device offers no endpoint of that transport at all, the address is left ALONE** — value and stamp both carry forward untouched — rather than being overwritten with the other transport's. That is the conservative branch and it is deliberate: the alternatives are to clobber the tuple (the bug) or to drop a server whose device merely stopped advertising one of its two endpoints, so accepted staleness is the trade, exactly as the `ipmiHost` matrix's row 6 makes it. The coupling also runs the other way, because `host` + `port` + `protocol` + `username` describe ONE console endpoint: the endpoint counts as accepted only when BOTH halves of the address are taken, and the protocol stamp and the endpoint's username are written only then. A retained hand-edited address therefore keeps the record's own protocol and username, so a transport flip at the source cannot reset the protocol out from under an endpoint the sync deliberately did not take (leaving, say, SSH aimed at a retained telnet box).

**Host/port are sync-owned with hand-off.** A synced server's primary `host` and `port` follow the same ownership discipline as `syncedProtocol` above. The rule is provider-agnostic — it governs a NetBox SSH server exactly as it governs a lab node's telnet console — so it is stated once, in §4.12.1.

### 4.5 Port Forwarding
1. Create tunnel profile with `Nexus: Add Tunnel`. Choose tunnel type from the dropdown:
   - **Local Forward (-L)**: local TCP listener forwards to a remote target through SSH.
   - **Reverse Forward (-R)**: the remote SSH server listens and forwards incoming connections back to a local target.
   - **Dynamic SOCKS5 (-D)**: local SOCKS5 proxy routes connections through SSH to arbitrary destinations.
2. Assign a default server, or leave unassigned to choose at start time.
3. Start a tunnel from **Port Forwarding** (right-click > Start), or drag it onto a server in **Connectivity Hub**.
4. In shared mode (default), the SSH connection is established eagerly at tunnel start - 2FA happens once upfront.
5. Active tunnels show traffic counters (bytes in/out).
6. The **Port Forwarding** view shows live route and traffic counters for active tunnels, and marks tunnels owned by another VS Code window separately.
7. Connection mode can be profile-based: `isolated`, `shared`, or `ask every start`. Reverse tunnels always use shared mode.
8. Right-click tunnel item to start/stop/restart/edit/remove/duplicate/copy info/open in browser.
9. Route labels indicate tunnel type with `L`, `R`, or `D`.
10. Cross-window tunnel visibility: all three tunnel types are registered in globalState and visible across VS Code windows.

### 4.6 Serial Sidecar
1. Create a serial profile with `Nexus: Add Serial Profile` (name + group + line settings).
2. Select `Standard` or `Smart Follow` connection mode.
3. Profiles appear in **Connectivity Hub** and support right-click connect/edit/remove/duplicate/rename.
4. Run `Nexus: Connect Serial Port` (or item context action) to open an interactive serial terminal.
5. Active serial sessions are shown under the profile node in **Connectivity Hub**.
6. Unread output marks both the sidebar session node and the terminal tab title until the terminal regains focus.
7. Smart Follow mode tries the saved preferred port first, silently reconnects only when a free replacement matches the saved device metadata, prompts before switching to unfamiliar free replacement ports, updates the saved preferred port after a successful move, and keeps the terminal open while waiting or stopped if the device disappears or serial runtime errors occur.
8. Smart Follow sessions coexist with standard serial sessions as long as they target different ports. Starting any new serial session is blocked only when the target port is already held by another Nexus serial session; the warning toast names the existing session.
9. Use `Nexus: Disconnect Serial Session` from profile/session context menu or command.
10. `Nexus: List Serial Ports` reports detected ports and manufacturers for diagnostics.

### 4.7 Logging and Rotation
1. Terminal and tunnel event logs are enabled automatically.
2. Each log file rotates when it reaches configured max size.
3. Rotation defaults: `10MB` file size and `1` rotated file.
4. Session transcript logs record clean terminal output with ANSI escape sequences and control characters stripped. Transcript writes are queued in memory and flushed on an interval (250 ms) rather than written synchronously per chunk; every orderly exit — terminal closed, session disconnected, extension deactivated — flushes the queue explicitly, and rotation cuts the file at exactly the same byte boundaries as the synchronous writer did.
5. The per-chunk terminal data trace (`nexus.logging.terminalOutputTrace`) is **off by default** and is a troubleshooting aid only. When on, every chunk a session receives is written to the diagnostic log synchronously as it arrives — measurable latency on the terminal's output path, and a verbatim plaintext record of session data including anything echoed on screen (passwords, keys). Lifecycle logging (connect, disconnect, errors) is unaffected and always on.
6. Settings:
   - `nexus.logging.maxFileSizeMb`
   - `nexus.logging.maxRotatedFiles` (`0-99`)
   - `nexus.logging.sessionTranscripts` (enable/disable)
   - `nexus.logging.sessionLogDirectory` (custom path)
   - `nexus.logging.terminalOutputTrace` (per-chunk data trace; default off)

### 4.9 Terminal Macros
- Define named macros in the Macro Editor. Macro metadata is stored in VS Code globalState; secret macro text is stored in VS Code SecretStorage.
- **A macro's text round-trips through the editor byte for byte, leading blank line included.** That takes one deliberate character: the HTML parser discards a single U+000A immediately after a `<textarea>` start tag ("newlines at the start of textarea elements are ignored as an authoring convenience"), so `renderMacroEditorHtml()` emits `TEXTAREA_LEADING_NEWLINE` ahead of the macro's own text for it to discard. Without it the form opened already short a line, and `MacroEditorPanel` saves `msg.text` verbatim — deliberately, since a macro's text is sent to the terminal exactly as stored and trimming it would break a macro that ends in a bare newline — so opening the editor on such a macro and pressing **Save** with no edit at all rewrote it, with nothing reported. Fixed in 2.8.76; the line it replaced was a `text.replace(/\n/g, "\n")` that replaced newlines with themselves.
- Macros appear in the **Terminal Macros** sidebar view (`nexusMacros`).
- See the [Macro Guide](macros.md) for step-by-step setup, trigger scopes, cooldowns, intervals, and regex examples.
- Click the play button or the label to send macro text to the active terminal.
- Press `Alt+S` to open a quick pick of all macros.
- Each macro can have an explicit `keybinding` such as `alt+m`, `alt+shift+5`, or `ctrl+shift+a`. Right-click a macro and select **Assign Shortcut** to edit it.
- Conflict resolution: assigning a shortcut already taken by another macro clears the old assignment.
- Macros without a shortcut remain available via the `Alt+S` quick pick.
- If VS Code terminal/menu settings intercept macro shortcuts, run **Nexus: Fix Macro Keybindings** explicitly. Nexus no longer mutates those global settings during activation.
- Add `triggerPattern` to enable auto-trigger (expect/send). Matching terminal output sends the macro text automatically, with optional per-macro `triggerCooldown`.
- Existing macros with no trigger scope keep the compatibility default of matching all terminals. Secret prompts should use the safer `active-session` or `profile` trigger scope where practical.
- Add `triggerInterval` for polling-style macros. An interval macro starts only when its pattern matches the active terminal; that terminal owns delayed sends even if focus changes. Later matches on that same session send immediately if the interval has elapsed, or wait until it has.
- Add `triggerInitiallyDisabled` when a macro should start paused until you manually resume it from the macros view. If the prompt already matched recently, resuming can fire immediately without extra terminal output.
- Auto-trigger can be paused/resumed per macro from the macros view, and globally toggled with `nexus.terminal.macros.autoTrigger`.
- All auto-trigger state (paused/resumed, interval ownership, cooldown/scheduling timers) is keyed to a stable per-macro identity (`macroStateKey()` in `macroAutoTrigger.ts`: the macro's `id`, or a `name`+`text` composite when `id` is absent), never to the macro's array position. Reordering macros (**Move Up** / **Move Down**) or deleting a different macro cannot reattach one macro's paused/armed state to another — a fix in 2.8.74 for exactly that bug (a paused secret trigger could go live after an unrelated reorder moved it onto an active trigger's old slot, or vice versa).
- That identity is not guaranteed unique across an arbitrary macro set: `nexus.macros` can already contain two macros with the same `id` (or two id-less macros with identical `name` and `text`) because a build predating the uniqueness invariant wrote them, or because the stored list was edited by hand. It is no longer reachable through an import: replace-mode restore assigns a fresh id to every incoming record (`MacroStore.replaceAll()`), merge-mode restore drops any incoming record whose id the store already holds, and legacy `nexus.terminal.macros` absorption re-keys an absorbed record that collides with a persisted one (`assignIdsForAbsorbedMacros()`). Such a key is ambiguous, and `findAmbiguousMacroStateKeys()` makes every claimant of it compile **no** auto-trigger rule — it cannot fire at all, rather than possibly firing as, or instead of, its twin. `setDisabled()` refuses to record state under an ambiguous key and `pruneState()` evicts one that becomes ambiguous, so whichever macro keeps the key when the conflict is resolved never inherits a pause the user set while the key meant "either of these". The sidebar renders each claimant that HAS a `triggerPattern` with a warning icon and `Auto-trigger suppressed: another macro has the same internal id…`; a claimant with no pattern keeps its ordinary icon (`lock` / `symbol-parameter` / `terminal`), because it has no trigger to suppress and nothing to report — `MacroTreeItem` gates the warning on `identityConflict && macro.triggerPattern` and the tree tests require it. The Macro Editor refuses to save or delete a macro whose id is shared: it carries a render-time reference but no row position, so it has nothing to tell the twins apart with. Any list write assigns fresh ids and clears the conflict — **Move Up** / **Move Down** is the documented remedy, and it keeps working on a flagged macro because every command resolves its target through one shared primitive (`resolveMacroTarget()` in `services/macroMutation.ts`) that prefers the clicked row's position whenever the macro still at that position carries the same id, falling back to the id only when the row has moved. A reference that is both stale AND ambiguous is refused with a message naming the remedy, never resolved to a first match — which is what previously made **Remove Macro** on the second of two twins confirm the first one's name and delete the first one's record.
- "Ambiguous" there means **at capture time**, not at write time, and the distinction is the whole fix rather than a pedantic one. Any write leaves a duplicated id with exactly ONE holder — which twin keeps it is not fixed, and does not need to be: `assignUniqueMacroIds()` awards it in array order, while desktop persistence goes through `assignMacroIds(…, { keepIdIfPossible })`, so a secret whose vault value could not be read claims the id it arrived with ahead of array order and an EARLIER twin is the one re-keyed. Either way the very write that shifts the array out from under a reference also leaves that id with exactly one holder — and an ambiguity check made when the write lands sees a perfectly unique id and resolves, confidently, to a twin the user may not have clicked. Nothing in the post-write array distinguishes that from an ordinary stale index over a unique id, which every command is required to resolve. So `MacroRef` carries what was known about its id when it was taken (`MacroIdProvenance` in `services/macroMutation.ts`), sourced from the rendered row's own identity-conflict flag (`MacroTreeItem.identityConflict`, which predates even the click) or from the list the command read before its first `await`; a reference taken over a shared id is honoured only by an exact row-and-id match and never falls back. Every capture site goes through `captureMacroRef()` / `captureMacroRefFromRow()`, and the field is required rather than optional so a new call site cannot inherit the guessing behaviour by omitting it. A drop is a separate gesture, arbitrarily later, so drag-and-drop needs that same witness — but it is deliberately **not** put on the wire. `handleDrag` keeps the reference it captured host-side (`MacroTreeProvider.lastDragCapture`) and serializes only the macro's `id`, the row's `index`, and a `dragToken` that is a lookup key and nothing more; a drop is given the retained capture only when the payload names the same token **and** the same id, and otherwise gets what the payload alone is worth — `"unverified"`, which rule 2b refuses when its claimed position no longer carries that id. A provenance flag written into the payload would have been the same bytes whoever wrote it, so a forged, stale or defaulted `"checked, and it was unique"` read exactly like an honest one; it was removed rather than validated. The Macro Editor's form is the same trust boundary and takes the same shape: its page carries back only the render-generation key it was drawn with, and the panel looks the reference up under that key host-side (`renderedRefs`, the last 8 renders), refusing a key it does not recognise or one whose recorded id is not the id the message names.
- The store never repairs ids on a **load** path. `VscodeMacroStore.reloadFromState()` preserves stored ids verbatim and does not write to the vault; `persistLegacyMigration()` keeps every already-persisted id and only re-keys records being absorbed from settings.json. Uniqueness is enforced solely at write time, by `MacroStore.save()` / `MacroStore.replaceAll()` (`assignMacroIds()`). The reason is that deciding which of two macros sharing an id owns the single vault entry at `macroSecretKey(id)` is unanswerable — duplicate secret saves predating the invariant were last-write-wins — so any load-time award would either hand one macro another's password or delete the only copy of a legitimate secret.
- Nothing on the activation path may call `MacroStore.save()`, and as of 2.8.74 nothing does. This is a requirement, not a description: the store's change listener reaches `MacroAutoTrigger.reload()` synchronously, so a save at startup would re-key a duplicate-id pair and compile **both** twins before the user ever saw the warning — turning the fail-safe into the exact failure it exists to prevent (a secret twin auto-sending the other's password). The one activation-time caller that existed, `migrateMacroSlots()`, was removed in 2.8.74; its work is now a read-time normalization inside the store (`withMigratedSlot()`).
- Related consequence, also 2.8.74: `SecretStorage.get()` returns `undefined` — it does not reject — when the OS keyring is unavailable, which is indistinguishable from "no entry". Every secret macro then resolves to empty text, so any subsequent save used to rewrite every vault entry with an empty string. `VscodeMacroStore` now records which secrets failed to resolve and refuses to overwrite their vault entries with `""`. The stated trade is that a secret which cannot be read also cannot be deliberately cleared until the keyring answers again.
- Vault write ordering is a crash contract: a secret's value is stored, `nexus.macros` is written next, and vault deletes happen **last**. That order never deletes the only durable copy of a value being moved to a new key, and a crash between the store and the commit leaves an entry that `Complete Reset` still finds. What makes the second half true is `SecretStorage.keys()` (`readVaultSecretIds()`): `clearAll()` asks VS Code which of this extension's secret keys exist and sweeps the union of that answer and its own in-memory list, filtered to the `macro-secret-text-` prefix so that server passwords, key passphrases, proxy credentials and auth-profile secrets — which share the namespace — are never touched. The answer is a strict superset of anything Nexus could have written down: `keys()` is documented as every secret stored by this extension, with no qualification by vintage, and the per-extension namespacing of secret keys has not changed, so entries written by older builds enumerate exactly like new ones. The prefix filter and the fact that the sweep deletes `macroSecretKey(id)` rather than the enumerated key are both load-bearing and both test-covered. `engines.vscode` is `^1.105.0` — the release in which `keys()` was finalized — and the call is unconditional.
- **Removed in 2.8.74, deliberately, and it should not come back.** Nexus used to maintain its own record of "vault keys this extension may have written", so that `clearAll()` had a list of keys to try: first the `nexus.macros.secretIds` array in `globalState`, then one marker FILE per secret id under `context.globalStorageUri` alongside it. Both imposed an ordering contract on every write path (grow the record before `secrets.store()`, shrink it after the delete) and the marker write was fail-closed, so an unwritable storage folder failed a save. Both were also cross-window read-modify-writes over shared state and could therefore lose an id, and three successive review rounds each found a fresh way for one to strand or leak an entry. None of that is fixable by ordering, because the write that UNNAMES an entry happens after the writes that name it. Enumeration is not a record of what was written but a question asked of the thing that holds it, so it has no such race — which is why the whole class was deleted rather than repaired. Nothing reads either record now, and the only write left is one line: `clearAll()` erases `nexus.macros.secretIds` alongside `nexus.macros`, keeping Complete Reset's "All Nexus data has been deleted" true of the bytes as well as of the behaviour. That cost a line rather than a mechanism because `clearAll()` was already writing `globalState`; a FIRST-RUN cleanup was still not added, because erasing bytes nothing reads on every activation needs either an unconditional write on the load path or a "have I cleaned up yet?" flag, and that is more machinery than the bytes cost. Between an upgrade and the user's first Complete Reset a profile therefore keeps whatever `nexus.macros.secretIds` it had, which is harmless: it is inert, so a stale id in it can cause neither a wrong deletion nor a missed sweep. The key is spelled inline at its one use site rather than as a module-level constant beside `MACROS_KEY`, so that nothing in the source reads as live state. The marker files never shipped in a release.
- `MacroStore` has two write entry points, split by PROVENANCE of the input, and the split is load-bearing rather than stylistic. `save()` takes a list DERIVED from `getAll()` — every macro command, the editor panel, share import, and merge import — and may therefore treat an incoming record carrying a currently-held id as the store's own record under that id, which is what lets it keep an unreadable secret pinned to the vault entry it cannot carry. `replaceAll()` takes a wholesale EXTERNAL list (replace-mode backup restore) and assigns a fresh id to every record before anything else runs, because an id in a file is an identity from another machine and any agreement with a local id is a collision. Handing external records to `save()` let an imported `secret: true` record with empty text (its backup blob undecryptable) inherit a colliding local macro's vault entry during a keyring outage, and resolve to that password once the keyring recovered — credential reassignment, fixed by the split. TypeScript cannot express the precondition, so it is enforced at the entry points and the caller list is enumerated in `MacroStore.save()`'s doc comment. One consequence had to be paid for at the merge-import call site: because replace mode freshens every id, the ids in a backup file no longer name anything after a replace-mode restore, so merge-mode import deduplicates on the macro's CONTENT key (`keyOf()`, the same one share import uses) as well as on its id. Without that, restoring a backup and later merging the same file added a second copy of every macro in it, each with its own id — so the ambiguous-id fail-safe suppressed neither and both auto-triggers fired on one match. `keyOf()` names every field that makes two records different macros — name, `secret`, the effective shortcut, text, the complete trigger configuration (`triggerPattern`, `triggerScope`, `triggerProfileId`, `triggerCooldown`, `triggerInterval`, `triggerInitiallyDisabled`) and every field of every declared variable, not just the names — because a collision on this key is a silent DROP rather than a merge: any field omitted from it is a field two legitimate macros can differ in while the incoming one is discarded with no report. It is built with `JSON.stringify` over a fixed tuple rather than a delimiter join, so a value containing the delimiter cannot forge another record's key.

  Being too SPECIFIC is the opposite bug and equally reachable, so every term names what the RUNTIME can observe rather than the field as spelled on disk. The canonicalization is shared (`canonicalMacroSecret()` / `canonicalMacroBinding()` / `canonicalMacroTriggerTerms()` / `canonicalMacroVariableTerms()` in `storage/macroStore.ts`), each collapse citing the `MacroAutoTrigger.reload()` line it mirrors: `secret` is TRUTHY (legacy absorption persists `secret: "true"`), the shortcut is `getAssignedBinding()` so a legacy `slot` participates and `alt+1`/`Alt+1` agree, an absent `triggerScope` is `"all-terminals"` (the editor always writes the default, `sanitizeImportedMacro()` never does), `triggerInterval` is normalized the way the compiler reads it, and with no `triggerPattern` the entire trigger group is inert and keys as absent. `triggerCooldown` is deliberately NOT collapsed against its default, because the default is the `nexus.terminal.macros.defaultCooldown` SETTING: absent means "follow the configured default" and an explicit `3` means "pin to 3", which differ the moment the setting is changed. `keyOfLegacy()` in `vscodeMacroStore.ts` is a different key for a different question — whether a record already in `nexus.macros` is absorbed from settings.json AGAIN, on every activation — but it now shares that canonicalization, and the only things it may omit are what the `withRedactedVariables()` boundary destroys: a secret macro's text (keyed as `__SECRET__`) and a MASKED variable's `default`/`remember`. Generalizing that exemption into "leave the trigger configuration out" cost real macros: absorption dedupes BEFORE persisting and then clears the setting, so two legacy records differing only in cooldown, interval, scope, target profile, start-paused or `slot` collapsed and the loser was gone for good.
- A save publishes THIS WINDOW'S WHOLE VIEW of the macro list, secrets included, and that is the entire cross-window rule. `nexus.macros` is rewritten wholesale (it always was) and every secret whose value this window holds is written back to the vault — including one whose value has not changed, with the same bytes it was read with. What it guarantees: a record `nexus.macros` names as `secret: true` is written together with the vault entry behind it, so a stale window republishing a macro another window deleted (or wiped with `Complete Reset`) restores it WHOLE rather than as an empty secret nobody is told about. What it costs, stated plainly: a window holding a stale snapshot reverts another window's concurrent edits — a name, a trigger, an order, and now the secret value too. Two earlier designs tried to keep the other window's newer secret by not rewriting an unchanged one, first unconditionally and then after reading the key back and restoring it only when it had gone; both published a MIXTURE of the two windows' views, and the read-back cannot be correct in principle because `SecretStorage` has no compare-and-swap, so the check is separated from the `nexus.macros` commit it guards by every remaining `await` in the save. What is NOT guaranteed: another window's delete landing between this save's `secrets.store()` and its `nexus.macros` commit still publishes a record naming an entry that is gone, and another window's store landing in that same gap is overwritten. Both need a genuine interleaving inside one save rather than merely a stale snapshot, and neither is fixable at this layer — `globalState` and `SecretStorage` expose no compare-and-swap and no shared lock. Within ONE window there is no gap at all: **every** mutating entry point on `VscodeMacroStore` runs through one `runExclusive()` chain — `save()`, `replaceAll()`, `saveFolders()` and `clearAll()` as of 2.8.75 — so a `Complete Reset` issued while a save is blocked on an OS keychain prompt runs after it rather than through it. That is a requirement on the class, not a description of four methods: a new public writer that does not enlist can interleave its `globalState.update()` with another writer's, and `globalState` has no compare-and-swap to notice. `saveFolders()` shipped outside the chain in the folders work and was caught only at the merge, because `runExclusive()` and `saveFolders()` came from different branches and neither branch was wrong on its own.
- Secret macros support **Copy Value** and **Paste Value** from the macros view context menu. Copying writes the macro value to the OS clipboard as plain text.
- Pasting into a secret macro reads the current clipboard text and can optionally append a trailing newline before saving. Both of those are `await`s, and the append-newline prompt is an ordinary (non-modal) notification, so the window stays usable while it is up — **Paste Value** therefore re-checks *both* preconditions against the macro as it stands at the moment of writing, not as it stood when the menu opened. If the macro was deleted meanwhile, nothing is written. If it stopped being a secret macro meanwhile (unticking **Secret** in the Macro Editor and saving), nothing is written either, and Nexus says why: writing then would have removed the value from SecretStorage and stored the clipboard text in plain text under `nexus.macros`.
- Legacy `slot` values are still read, and normalized to `keybinding` as the store resolves them — in memory, with no write. The stored record keeps its `slot` until the next save you actually ask for, which persists the migrated shape. A macro carrying both a `slot` and an explicit `keybinding` keeps both; the `keybinding` already wins everywhere.
- Add, edit, remove, reorder, pause/resume auto-trigger, and assign shortcuts via the context menu.

#### 4.9.1 Macro Templates
- `Nexus: Add Macro From Template` opens a starter-template picker and then opens the Macro Editor on the created macro.
- Built-in templates are **Send command**, **Send password when prompted**, **Wait and send confirmation**, **Scoped auto-trigger example**, **IPMI SOL console**, **IPMI Power Status**, **IPMI Power On**, **IPMI Power Off (hard, no OS shutdown)**, and **Launch IPMI web console** (see 4.9.2).
- The four IPMI templates all ship as `runIn: "localTerminal"` with `-E` (password from the environment, never argv) and `provideIpmiCredentials: true`. A template insert is a LOCAL action rather than an import, so `IMPORTED_CAPABILITY_FIELDS` never strips their flag — the extension vouching for its own command, on this machine, at the user's request. **IPMI Power Off** carries its destructiveness in its name and description (it is an abrupt power cut, not an OS shutdown); no per-macro confirmation mechanism was invented for it, since the text is visible in the picker and the editor before anything runs.
- The password template creates a secret macro with empty text, an active-session trigger scope, a password prompt pattern, and start-paused enabled. It stores no sample password; the user must enter and save the secret, then resume auto-trigger from the macros view before it can auto-send.
- Auto-trigger templates default to active-session scope so generated macros react only to the active terminal unless the user changes the scope.

#### 4.9.2 Macro Variables
- A macro can declare up to 10 named variables (`MAX_MACRO_VARIABLES` in `macroVariables.ts`) and prompt for them at run time instead of sending fixed text. Each variable has a `name` (`/^[A-Za-z_][A-Za-z0-9_]{0,31}$/`), an optional `label` (defaults to the name), an optional `default` (not allowed when masked), a mask-input flag (`secret`, never persisted or remembered), and a remember flag (non-secret values remember their last-entered value per VS Code window unless turned off for that variable).
- Reference a declared variable in the macro's text as `$name` or `${name}` — both forms resolve once `name` is declared. `$$name` / `$${name}` is the escape for a literal `$name` / `${name}`. A placeholder whose name is not declared is passed through to the terminal untouched, whether written as `$name`, `${name}`, or the `$$`-escaped form — this is deliberate (a typo fails silently rather than blocking the macro) and the Macro Editor's live hints under the Text field are the mechanism for catching it (undeclared-placeholder warning with a one-click "Add variable" fix, declared-but-unused notice, or a "Will prompt for: …" confirmation).
- Only declared variables whose placeholder actually appears, unescaped, in the text are prompted for — once each, in declaration order.
- Runtime flow (`src/commands/macroVariablePrompt.ts`): the target terminal is pinned to `vscode.window.activeTerminal` at invocation, before any prompt is shown. A single reused `InputBox` walks the used variables in order; each step shows a **Back** button except the first. Accepting a step records its value (and remembers it, per the variable's remember flag) and advances; Back steps back one; any other dismissal (Esc, a button other than Back) cancels the entire run — no partial send; the input box sets `ignoreFocusOut = true`, so clicking away does not close it. A masked step never prefills from a remembered value, a default, or a previously entered value for that same step. Once every used variable is collected, the substituted text is sent to the pinned target terminal via `terminal.sendText(text, false)`, even if a different terminal is now active. Only one variable-prompt macro run can be in flight at a time; invoking a second one while the first is still prompting shows a status-bar message naming the busy macro instead of queuing or interleaving prompts.
- This prompting path bypasses VS Code's own `Terminal.sendText`-driven variable resolution — `${workspaceFolder}` / `${env:FOO}`-style tokens in a variables-macro's text are sent to the terminal literally rather than resolved, unlike the plain (variable-free) send path.
- Variables and auto-trigger (`triggerPattern`) are mutually exclusive on the same macro: prompting requires opening a foreground input box, which cannot happen safely from a background pattern match against a possibly-inactive terminal. The Macro Editor surfaces this as a live warning next to both the Variables section and the Auto-Trigger Pattern field the moment a macro carries both. Config import sanitization strips the trigger in this case; a macro that reaches this state some other way (legacy `nexus.terminal.macros` settings absorption, or a direct edit to stored state) renders in the sidebar as a plain, non-auto-triggering macro — no zap icon, no enable/disable toggle — with tooltip text `Auto-trigger suppressed: macro has variables`.
- Variable macros get a `⌸` marker in the Run Macro quick pick; the Macros sidebar shows that same marker plus a distinct icon. Their sidebar tooltip lists the variable names the macro will actually prompt for.
- The **IPMI SOL console** template (4.9.1) builds ` ipmitool -I lanplus -H ${profile.ipmiHost} -U ${profile.ipmiUsername} -E sol activate` with `runIn: "localTerminal"` and `provideIpmiCredentials: true`, and declares **no variables at all** (issue #48 PR-B). The originating feature request's worked example is now end to end off the server profile: the BMC address from **IPMI / BMC Host**, the BMC username from the linked **IPMI Auth Profile**, and the password from that profile's vault entry through `IPMITOOL_PASSWORD`/`IPMI_PASSWORD` — so no prompt, and no secret on the command line. The `-P $password` form still works for a user who writes it; it is simply no longer what ships.
- No automatic quoting: substituted values are inserted exactly as entered. See the [Macro Guide](macros.md) for the `'${password}'` single-quote idiom (a deliberate choice — network-device CLIs like Cisco IOS would have a value corrupted, not protected, by auto-quoting) and the `HISTCONTROL=ignorespace` leading-space convention for keeping a value out of the remote shell's own history.

#### 4.9.3 Macro Folders
- `TerminalMacro` carries an optional `group: string` — the same shape servers, serial profiles, and Local Shell profiles already use for the Connectivity Hub. Explicit folders (empty or not yet holding any macro) persist separately under globalState key `nexus.macros.folders` (`MACRO_FOLDERS_KEY` in `vscodeMacroStore.ts`), managed by `MacroStore` alongside `nexus.macros`. `clearAll()` clears it; import/export carries it the same way the Connectivity Hub carries `nexus.groups`. It is NOT managed alongside `nexus.macros.secretIds`, which nothing reads or grows any more — that key survives only as the one erasure `clearAll()` performs on it (see above).
- The rendered folder set is the union of the explicit-folder list and every folder implied by a macro's `group` (ancestors included), matching `collectGroups()`'s treatment of servers.
- **`group` is untrusted at every read site** (`sanitizeMacroGroup()` / `macroGroup()` in `src/services/macroFolders.ts`): a non-string, `".."`, an over-depth path, or a pathologically long string all canonicalize to `undefined` rather than throwing or stalling the extension host, so such a macro simply renders at the root. `""` and a missing `group` are indistinguishable — both render at the root. The length bound (`MAX_FOLDER_PATH_LENGTH = 4096`, POSIX `PATH_MAX`) is checked before the string is ever split, so rejecting an eight-million-character value costs nothing; it exists solely to bound a pathological allocation and is deliberately above what a real filesystem could produce at `MAX_FOLDER_DEPTH` (10 × `NAME_MAX` 255 + separators = 2559), so it never polices how you name a folder.
- **Reading sanitizes; storage is never rewritten.** A folder path you have already stored is treated as committed data: neither activation, nor settings absorption, nor saving an unrelated macro rewrites or deletes it. Ingest (`dropNonPathGroup()`) drops only a value that holds no path at all — a non-string, or a blank string — because there is no assignment there to preserve. A stored string that no longer satisfies the grammar (say `Cisco\Routers` typed with a Windows separator) is kept byte-for-byte and shown at the root until you correct it, rather than silently vanishing. Validation happens where you can act on it: the Macro Editor's Folder field, the New Folder box, the folder picker, and `sanitizeImportedMacro` on the config-import path. The Macro Editor is where that correction actually happens, so it shows the stored value **verbatim** in the **Folder** field with a note explaining why the macro sits at the root: leave the field alone and the macro saves with its folder path untouched (editing only the name never rewrites it); change the field and the value goes through the normal grammar, so any edit is a deliberate, validated decision. The one exception is a stored path longer than the 4096-character bound — it is withheld from the editor rather than shipped into the webview, so the field stays blank with its own note, the value is still preserved on save, and **Move to Folder → (root)** is how you clear it. The eager `MACROS_KEY` rewrite on reload is reserved for scrubbing a masked variable's plaintext default — a secret — and never fires for `group`. The persisted folder list is the one exception: an entry there *is* a path and nothing else, so an unrenderable one has no representation in the tree at all and is dropped as a corrupt record.
- `MacroTreeItem.index` is always the true index into the full `getMacros()` array, never a per-folder ordinal — folders are a display projection over the flat array, so assigning, renaming, or clearing a macro's folder rewrites one field in place and never reorders anything or perturbs another macro's index.
- Folders sort by natural path comparison and render before macros; macros keep array order both inside a folder and at the root, so **Move Up** / **Move Down** (swapping with the nearest macro sharing the same folder, which may not be array-adjacent) and the flat **Run Macro** quick pick stay meaningful.
- Commands: `nexus.macro.newFolder` (view-title button), `nexus.macro.moveToFolder` (a tree item moves just that macro; the Command Palette with no selection opens a multi-select quick pick of macros first, then a folder picker), `nexus.macro.addToFolder` (opens the Macro Editor with the Folder field pre-seeded), `nexus.macro.renameFolder` and `nexus.macro.removeFolder` (re-parents every descendant macro to the removed folder's parent — or the root — preserving nested sub-structure; never deletes a macro). A rename is a prefix substitution, so a longer name lengthens every descendant path: if any resulting path would cross the 4096-character bound — which would make those macros unrenderable and drop them to the root — the rename is refused outright with an explanation and nothing is written, rather than half-applied.
- Drag and drop: a macro tree row drags with its own MIME type (`application/vnd.nexus.macro`, distinct from the Connectivity Hub's tunnel/profile MIME so the two views don't advertise cross-acceptance) and a payload of `macro.id`, the dragged row's `index`, and a `dragToken` keying the host-retained capture (§4.9) — the index is honoured only while the macro at that position still carries the dragged id, so a concurrent array change can't rewrite the wrong macro's folder. Dropping onto a folder sets that macro's `group`; dropping onto another macro targets that macro's own folder; dropping onto the root clears `group`. Folders themselves are not draggable. The tree has no multi-select — bulk moves go through `moveToFolder`'s own quick pick instead.

### 4.10 Configuration Export/Import
- `Nexus: Export Configuration` creates a sanitized JSON export suitable for sharing (credentials stripped, learned Smart Follow hardware identifiers removed, IDs remapped).
- `Nexus: Export Backup` creates an encrypted backup that includes profiles, settings, saved credentials, the user `.ssh` folder, and the configured Nexus scripts folder.
- `Nexus: Import…` is the single universal entry point (retitled from `Nexus: Import Configuration`, which used to accept only Nexus's own JSON). It opens a `QuickPick` titled **Import** ("What are you importing?") with six rows under three separators — bulk host-list add first (**Paste Host List from Clipboard**, **Host List File…**), migration from another client second (**MobaXterm INI File…**, **SecureCRT XML Export…**, **SecureCRT Sessions Folder…**), and **Nexus Export File…** last (it's the only branch with a destructive Replace mode, so it's deliberately off the default-focused row) — then dispatches to the matching branch in `configCommands.ts`. It is reachable from the Connectivity Hub's `...` overflow menu (`view/title`, group `1_manage@2`, next to **New Folder**) so it's available even once the tree isn't empty, from the Connectivity Hub's empty-state welcome view (second link, after **Add Profile**), and from the Data Management section of Settings (single **Import…** row, `cloud-download` icon).
- Not every branch guards its input size, and not every branch sniffs. **Host List File…**, **MobaXterm INI File…**, and **Nexus Export File…**'s failure path each read a dialog-picked file and then sniff the content with `sniffImportFormat()` (`src/utils/importFormatSniffer.ts`, no `vscode` import — pure `{`/`<`/`[Bookmarks(_N)]`-header detection, defaulting to `host-list` for everything else). Sniffing only ever *contradicts* the declared format; it never chooses one (a generic INI's `[General]` header would otherwise parse as a valid server named "General" once `HOST_RE`'s IPv6-bracket tolerance strips the brackets — this is why content-detection isn't the primary mechanism). When the sniff confidently indicates a different supported format, the branch stops with a named error plus a one-click button that re-parses the **same already-read bytes** through the right importer (no re-opened dialog, no re-asked source); **Host List File…**'s contradiction also offers a second button, **Import as Host List Anyway**, so a genuine host list the sniffer mis-flags (say, a hostname list whose first line happens to start with `{`) still has a way through instead of a dead end. Otherwise the branch proceeds into that format's existing parser and tail unchanged. The **SecureCRT XML Export…** / **SecureCRT Sessions Folder…** branches never sniff — they validate content structurally instead (`parseSecureCrtXmlExport`, `hasSecureCrtSessionsRoot`) — and neither does **Paste Host List from Clipboard** or the `.inventory` deep link's file path; both go straight into the inventory parser. Regardless of sniffing, the host-list parser and the SecureCRT XML parser are each capped (2 MB, 10 MB) at a shared tail function (`applyInventoryText`, `applySecureCrtXmlText`) that every route funnels through — the direct dialog **and** every cross-branch reroute — so a reroute can never hand either parser more bytes than its direct route would accept. The MobaXterm and Nexus Export File dialogs have no size guard at all.
  - **Nexus Export File…**: JSON.parse + `isValidExport` failure gets format-aware messaging instead of always pointing at the CSV importer — sniffed as a host list → "That file isn't a Nexus JSON export." + **Import as Host List**; sniffed as MobaXterm → **Import as MobaXterm**; sniffed as XML → **Import as SecureCRT XML**; syntactically valid JSON that just isn't shaped like an export → a generic "valid JSON, but not a Nexus export" message with no button (nothing to reroute to); syntactically broken JSON that still starts with `{` gets its own "could not be parsed as JSON" message rather than being called "valid JSON". Also accepts a minimal hand-written JSON file (`{ "version": 2, "servers": [...] }`) for a single connection or a quick script.
  - **MobaXterm INI File…** / **SecureCRT XML Export…** / **SecureCRT Sessions Folder…**: `Nexus: Import from MobaXterm` and `Nexus: Import from SecureCRT` remain in the command palette as direct shortcuts into the same branches (`.securecrt` keeps its own XML-vs-folder picker). No `[Bookmarks]` section → named error with a reroute when the sniff points elsewhere; a SecureCRT XML whose root lacks `<VanDyke><key name="Sessions">` entirely (as opposed to having it with zero SSH entries inside, or every entry skipped — all "nothing new" outcomes previously returned the same empty result from `parseSecureCrtXmlExport`, distinguished now via the additional `hasSecureCrtSessionsRoot()` export in `securecrtParser.ts`, called only when the parse came back fully empty) gets a dedicated "isn't a SecureCRT export" message; a Sessions folder with zero `.ini` files gets a dedicated message naming the expected `%APPDATA%\VanDyke\Config\Sessions` location. The XML branch's file picker offers an "All Files" filter alongside "SecureCRT XML Files" and does not gate on the `.xml` extension — a renamed export still imports, since content validation (not the file suffix) is what actually distinguishes a SecureCRT export from anything else; only a selected directory is rejected outright with the generic "Unsupported SecureCRT input" message.
  - **Paste Host List from Clipboard** / **Host List File…**: bulk-creates servers from a pasted or file-based device inventory (`src/utils/inventoryParser.ts`). `Nexus: Import Servers from List (CSV/Text)` remains in the command palette as a direct shortcut (keeping its own clipboard-vs-file picker). Accepts an optional header row (columns matched by alias, e.g. `hostname`/`address`/`ip` → host — two or more alias matches are decisive even if an unrecognized column contains punctuation like `mgmt.ip`; a single-column list whose sole row is itself an alias is treated as an ambiguous header and reported as an issue rather than silently dropped), or a positional `host[,name[,username[,port[,folder]]]]` fallback (a 3-field row reads its third column as a username, not a folder) with `user@host:port` shorthand in the host field; comma- and tab-delimited (empty fields preserved), or whitespace-run-delimited (runs collapsed). Hosts are capped at 253 characters and names at 128; both cap violations, and an invalid row-level or prefix folder path, are reported as issues rather than silently accepted or discarded. Capped at 2 MB and 5000 rows — rows are collected without over-allocating past the cap, and truncation reports the real dropped-row count, not just a single generic issue entry. Rows missing a username trigger a single default-username prompt (stating how many rows need it, pre-filled with the most common username among existing servers); the optional folder-prefix prompt is skipped entirely when the list already carries its own folder column, and Esc cancels the whole import from either prompt (an empty Enter on the folder prompt just skips the prefix). Rows whose host+port+username (host compared case-insensitively) already exist are skipped and counted, and the folders they would have created are dropped too so no empty group is left behind; if every row already exists, the message says so plainly instead of pairing a skip count with "no sessions found". Everything culminates in a single confirm modal (`showInformationMessage` with `detail`) summarizing servers to import, folders to create, duplicates to skip, and unparsable/truncated rows, with an additional "Show Skipped Lines" button that opens a scratch document without importing; the apply step runs through `NexusCore.addServersBatch` (one `saveServers`/`saveGroups` write and one change notification for the whole import, instead of one round-trip per row) inside a non-cancellable `withProgress` (the batch is a single write, so there is nothing to cancel). Any remaining parse issues are reported afterward via a **non-awaited** toast so a corner notification the user ignores can never stall the import. Imported servers always get `authType: "password"`.
- The MobaXterm/SecureCRT importers still funnel through the shared `applyImportedSessions` tail in `configCommands.ts` (no-sessions warning, single confirm modal, group + server creation, success toast — pluralized without the "(s)" shorthand), which mints a fresh server `id` per row. The inventory importer above has enough UX differences (dedupe-aware wording, the detail-modal breakdown, batched apply) that it keeps its own tail instead of extending the shared one. `importInventory`'s source acquisition (clipboard/file) is split from its parse-and-apply tail (`applyInventoryText`) so the chooser's clipboard/file rows, the `.inventory` deep link, and cross-branch "Import as Host List" reroutes all share it.

### 4.11 Terminal Tab Commands
Right-click any Nexus terminal tab (SSH, Standard Serial, or Smart Follow Serial — docked in the panel or opened as an editor tab) to access three PuTTY-style commands:

- **Reset Terminal** — clears the visible terminal screen while preserving scrollback. The noisy or scrambled output is pushed up into scrollback where it can still be reviewed. The underlying session and terminal modes are untouched; the remote shell receives nothing. Use this when stray output clutters the screen but you want your history intact.
- **Clear Scrollback** — clears both the visible scrollback and the Nexus-maintained capture buffer. After running this command, *Copy All to Clipboard* returns only post-clear output. Note that clearing the terminal via VS Code's own built-in clear (from other surfaces) does NOT clear the Nexus capture buffer; only this command keeps them in sync.
- **Copy All to Clipboard** — copies the ANSI-stripped transcript of the session to the system clipboard. A toast reports the number of lines copied; an empty buffer shows "Nothing to copy." instead. The capture buffer's size tracks your `terminal.integrated.scrollback` setting and updates when that setting changes.

After a session disconnects but before the terminal tab is closed, *Reset Terminal* and *Clear Scrollback* grey out (nothing to act against), while *Copy All to Clipboard* remains enabled so you can still capture the full transcript for a ticket or chat. All three commands are also discoverable from the Command Palette, gated on an active Nexus terminal.

**Extension reload / disable / update.** When the VS Code window reloads, the extension is disabled, or Nexus is updated, VS Code does not reliably deliver a final write to the terminal before the extension host exits (it races the 1–4s shutdown timeout and the pseudoterminal IPC channel — see [microsoft/vscode#122825](https://github.com/microsoft/vscode/issues/122825) and [#140697](https://github.com/microsoft/vscode/issues/140697)), so any in-tab farewell banner is best-effort only. Instead, the next time the extension activates, Nexus scans `window.terminals` for its own naming pattern (`Nexus SSH:` / `Nexus Serial:`) and, if it finds any, shows an information notification — e.g. *"Nexus: 3 sessions disconnected after an extension reload or restart. The tabs are frozen on their last output — close them manually when you are done reviewing. Reconnect from the Connectivity Hub when ready."* The zombie tabs are **not** auto-closed: the last-rendered content (command history, log tails, error output) is usually worth reviewing, and closing is left to the user.

**Capture-buffer semantics** (implementation notes that surface in edge cases):

- The capture buffer is sized in **lines**, not bytes, matching the `terminal.integrated.scrollback` setting. A realistic interactive shell newline-terminates output promptly, so the retained size is well-bounded (~80 KB per session at the default 1000-line cap, 80-char average). A single never-terminated output (e.g., a raw binary paste with no `\n`) will accumulate in the pending-line fragment until a newline arrives or the terminal closes.
- An unfinished line (no trailing `\n`) still counts as one line in the "Copied N lines" toast and is included in the copied text — so a prompt like `switch> ` with no Enter yet adds 1 to the reported count.
- Setting `terminal.integrated.scrollback` to `0` does not disable Nexus capture; the buffer falls back to a 1000-line default so that *Copy All* and *Clear Scrollback* remain useful. If you need zero retention, close the terminal tab.

### 4.12 Inventory Sync

An **inventory source** is a saved provider configuration that creates and maintains server profiles from an external system of record. Two providers ship built in — NetBox (§4.12.3) and EVE-NG (§4.12.4) — registered against `InventoryProviderRegistry` in `activate()`; a third-party extension can register its own through the public API (`src/publicApi.ts`, which documents the trust model, since VS Code exposes no caller identity to `registerInventoryProvider`). Everything from §4.12.1 to §4.12.3 is provider-agnostic or NetBox-specific; §4.12.4 onward is EVE-NG. (These topics were numbered 4.4.5–4.4.8 through 2.8.188, nested under **SSH Terminal Session**, which they were never children of.)

#### 4.12.1 Sources, sync plans, and field ownership

**The source record.** `InventorySourceConfig` (`src/models/inventory.ts`) holds `id`, `providerId`, `name`, `targetFolder` (normalized; `""` means the tree root — allowed, discouraged), `prunePolicy`, `defaultUsername` (a fallback SSH username applied at ADD time only), the non-secret `config` values, and `secretFieldIds` — the password-type field ids captured at save time, so secret cleanup and backup do not depend on the provider still being registered. Secret values live in `SecretStorage`; nothing password-shaped is written to settings or `globalState`. Two further fields exist for identity rather than configuration: `revision`, an opaque generation token reassigned on EVERY write to the record (so a caller's already-captured snapshot can be told apart from a later incarnation, while a routine sync's `lastSyncAt` bump does not invalidate one), and `providerFingerprint`, a hash of the provider's observable shape (label + ordered config fields) at the last save — `syncNow` compares it against the current registrant BEFORE reading any vault secret, and a materially different shape under the same `providerId` is confirmed with the user rather than silently handed the saved credentials.

**The plan.** Nothing is applied blind: `computeSyncPlan` returns an `InventorySyncPlan` — `adds` (deterministic ids, `origin` set), `updates` (`{before, after}` full replacement objects), `prunes`, `unchangedCount`, `folders`, `warnings`, `hiddenPruneCount`, `manualDuplicateCount` and `adoptionCandidates` — and the apply step is separate. The three prune policies are `delete`, `orphan` (moved to `<targetFolder>/_orphaned`; the default) and `keep`. A fetch the provider itself truncated (its own hard cap or deadline tripped, see §4.12.4) sets `truncated`, which makes the plan **skip the prune phase entirely**: devices a capped fetch never reached must never read as absent.

**Field ownership — the stamp discipline.** A synced field is either sync-owned or hand-owned, and which it is is recorded rather than guessed. `ServerOrigin` carries `sourceId` / `externalId` / `syncedAt` / `syncedInstanceKey` plus one stamp per governed field — `syncedUsername`, `syncedAuthProfileId`, `syncedIpmiHost`, `syncedAltHost`, `syncedProtocol`, `syncedHost`, `syncedPort` — and a `templated` record for the device-template fields. The shared rule: **the stamp records what the SYNC wrote, and the sync writes only where the record still carries exactly that** (or already agrees with the device, which mints the stamp without changing the value). A value you edited by hand fails that test and is left alone, with its stamp carried forward VERBATIM — including as `undefined`, which is what keeps a cleared-value opt-out cleared. Carry-forward is load-bearing rather than cosmetic: an update fired for a completely unrelated reason (a device renamed at the source) rebuilds the whole `origin` literal, and a rebuild that forgot a stamp would re-arm the very field the user opted out of. Name and folder are not in this scheme — no user ever hand-typed them into a synced record, so they always follow the device.

**Host/port are sync-owned with hand-off.** This rule is provider-agnostic — it governs a NetBox SSH server exactly as it governs an EVE-NG lab node's telnet console, which is why it is stated here rather than in either provider's section. A synced server's primary `host` and `port` follow the same ownership discipline as the stamped fields above (and as `syncedProtocol`, §4.4.4), via the `ServerOrigin.syncedHost`/`syncedPort` stamps (task #29). Earlier builds wrote the device's address onto a synced server **unconditionally**, so a console address you edited by hand was stomped on the next sync. Now the sync only overwrites an address the record still carries exactly as the sync last wrote it (or the device's current one); an address you have edited by hand is **preserved**, and a device whose address genuinely moves is still followed. The same rule guards the addressless downgrade: a device that loses its console reverts a *sync-owned* address to the addressless placeholder, but a **hand-typed** console address is kept and the server stays addressed. A freshly synced server owns the address it was created with, and an adopted server owns the corroborated address it is adopted at — so both are followed on later syncs without a hand edit being invented. (A backup you export and import into a pre-task-#29 build loses these stamps, so that older build reverts to "device always wins" for `host`/`port`.) **Legacy-migration edge:** a server synced by a build from *before* task #29 carries no address stamp yet. Its stamp is minted on the first post-upgrade sync — but only if the record's address still equals the device's at that moment (matrix row 5a). If the device's address changed *between* the last pre-#29 sync and the first post-#29 one, the record no longer matches, so that first sync reads it as hand-edited and leaves it: the stamp is never minted, and the server stops following (and stops being healed or downgraded) until you re-align it by hand. This is the one-time cost of introducing the stamp without a stored-config migration, and it self-resolves the moment the address is corrected to the device's.

#### 4.12.2 Servers with no address yet (addressless placeholders)

A device with **no usable primary endpoint** — a stopped EVE-NG node, a VNC/HTML5-console node, a NetBox row with no IP — is no longer skipped. It is created as a visible **addressless placeholder**: `ServerConfig.addressless === true`, `host: ""`, and the `ADDRESSLESS_PORT` sentinel (`0`) in `port`. The flag is written ONLY by inventory sync — a hand-created server is never addressless, and `validateServerConfig` relaxes the empty-host requirement only when the flag is exactly `true` (any other value, a non-boolean included, keeps Host required). The branch is reached AFTER the empty-name and duplicate-id skips and BEFORE the invalid-port skip, deliberately: addressless is for a device with no endpoint AT ALL, never a swallow for malformed data.

**How it renders.** The tree row carries a `" (no address)"` description suffix and drops the `@host` from its description head; the tooltip's endpoint line reads `no console address yet` rather than `user@host:port`, so an empty host is never dangled after an `@`. **Copy Connection Info** prints `(no console address)`, the **Profile Actions** quick pick describes the row as `(no address)`, and a plan warning that has to name such a server's address renders `(no address)` instead of the nonsense `:0`. The sync discloses them in aggregate, never per device, in **ONE** line naming up to three examples — and the sync **owns** that line: neither provider emits an addressless aggregate of its own. The line has three shapes, because the number a user can act on is the total and the part they can act on is the split:

- placeholders **added** this sync only — *"N devices have no console address yet and were added without one (e.g. …)"*;
- added **and** standing placeholders — *"3 devices have no console address yet — 1 was added without one and 2 were already placeholders (e.g. …)"*;
- standing placeholders only, worded so it cannot imply this sync created anything — *"1 device has no console address yet and remains a placeholder (e.g. …)"*.

The engine owns it because the engine is the only layer that knows the **outcome**. A provider sees that a device has no console address; only the sync knows whether that device became a placeholder just now or has been one for weeks, and that distinction is the actionable part. Owning it here also removes a genuine double-report: a NetBox row that is both nameless and addressless used to be counted in the provider's addressless aggregate **and** in the engine's empty-name skip summary, and is now reported once, under the reason that actually stops it becoming a server. Up to 2.8.189 both providers pushed their own aggregate beside this one, so a sync showed **two** lines about intersecting sets of devices — neither wrong, together confusing.

A previously-addressed server this sync **downgraded** to a placeholder keeps its own separate twin line, deliberately: losing a working console address is a different event from never having had one, and it is the one of the two that warrants a second look.

**What refuses, and how.** Every feature that needs the console endpoint refuses rather than reaching for a transport against an empty host — which would prompt, read the vault, and then fail on a handshake to nothing. As with the telnet list in §4.4.4, the refusals differ by kind:

- **Refused out loud, naming the server** — **Connect**, **Test Connection**, **Deploy SSH Key**, **Browse Files** (SFTP), and every route into starting a tunnel: the command, dragging a tunnel profile onto the server, the auto-start-on-connect sweep and the edit-then-restart path all funnel through one guard. They share `addresslessUnavailableMessage` (`src/utils/protocolGuards.ts`), which is deliberately **provider-neutral**: the guard is handed no provider identity, and an addressless server can come from an IP-less NetBox row as readily as from a stopped EVE-NG node, so it must not prescribe an EVE-NG-specific remedy — it says the server has no console address yet, that it may be offline or its source has not assigned one, and to re-sync once it has. **Duplicate** refuses on its own reasoning: a duplicate strips `origin`, so the copy would be a MANUAL addressless record — an invariant violation that no sync could ever upgrade, and whose own refusal would tell the user to re-sync a source it has no link to.
- **Not offered, then refused anyway** — a placeholder is filtered out of the **Jump Host** and **IPMI Gateway** pickers (`sshInfrastructureCandidates` in `formDefinitions.ts`, exactly as a telnet server is), and a STORED id that has gone addressless since the choice was saved is refused before any credential is read. No picker can retract a saved choice, and a device stops long after one is made. `ProxySshFactory` throws ahead of `connectToJumpHost`, so no vault read or password prompt happens; `resolveIpmiGatewayServer` resolves `{kind: "unavailable", reason: "addressless"}`, kept strictly distinct from `{kind: "none"}` — a configured-but-unreachable gateway makes BMC dispatch **abort** with a message naming the reason, never silently fall back to running the command on the local machine. It also resolves FAST, rather than handing back a host-less server the run path would try to connect to and hang out the ~90 s connect-session timeout on.
- **Silently skipped, disclosed in aggregate** — **Connect Folder Servers** steps over the folder's placeholders and reports one count (*"N servers have no console address yet and were skipped — they will connect once the inventory source assigns an address."*). An EVE-NG lab folder is mostly stopped nodes, the documented common case, so the per-node refusal path would be a popup storm.
- **Untouched — the out-of-band path** — only the console endpoint is missing, so BMC machinery stays live. The per-device template cascade runs for a placeholder too: its OOB-oriented fields (`ipmiAuthProfileId`, `ipmiGatewayServerId`) take effect immediately, the console-inert ones (proxy, multiplexing, legacy algorithms, session logging) are written under their templated stamps ready for the upgrade, and the source-level auth-profile link is written even though it is inert without a console. `ipmiHost` itself follows its own ownership matrix on the downgrade path, so a device that is addressless for console purposes can still carry a BMC address — which is why an addressless-with-BMC server correctly keeps both BMC actions (§4.12.6).

**Editing one.** Host and Port are not `required` on the form for a placeholder: you open it to set OOB fields, not to invent a host. Typing a real host gives it an address and **clears the flag on save**; while the record stays addressless the save forces the sentinel port back regardless of what the Port field showed. That field seeds the **protocol-appropriate** default (telnet → 23, ssh → 22) rather than a hardcoded 22 — the form's Protocol→Port hook (§4.4.4 step 1) treats a shown port as automatic only when it equals the CURRENT protocol's default, so seeding 22 on a telnet placeholder read as user-owned, was never corrected, and typing a host saved a telnet server on the SSH port.

**Upgrade and downgrade.** A later sync where the device gains a console UPGRADES the same record in place — filling `host`/`port`/`protocol` and clearing the flag, keeping the row, its folder, its credentials and its settings. Losing the console DOWNGRADES it back, but only where the sync still owns the address (§4.12.1): a hand-typed console address is preserved and the server stays addressed, and the protocol rides with that decision, so a retained hand address never ends up spoken to over the reset default transport.

#### 4.12.3 NetBox Inventory Source

The first built-in provider (`src/services/inventory/providers/netboxProvider.ts`, id `netbox`). It has no long-form section here; the reference is the README's **NetBox Inventory Sync** feature entry and its *Sync Servers from NetBox* walkthrough, which cover the API token in `SecretStorage`, the device filter, the folder template (`{site}/{rack}` by default, plus `{location}`, `{role}`, `{tenant}`), virtual machines, the Removed-Device Policy, remove-and-re-adopt eligibility, the source's auth profile, the out-of-band address filling `ipmiHost`, and **Primary IP Family** (which family fills Host, with the other family's primary IP written to Alternate host).

What this section adds is what NetBox shares with every provider: §4.12.1's plan and ownership rules, and §4.12.2. The second is a **visible behavior change** for NetBox users — a device with no usable IP is now created as an addressless placeholder, counted in the plan's warnings, where builds up to 2.8.188 dropped it and reported *"N devices … had no usable SSH or telnet endpoint"* as a skip. The device stays in the tree with its folder and settings and picks up its address on the sync after NetBox has one.

The provider contributes **no** warning of its own about those devices. It emits the tree — the endpoint-less device — and the sync says what became of it, in the single line described in §4.12.2. This is a change from 2.8.189, which pushed *"N devices have no usable SSH or telnet address in NetBox."* beside the engine's line; the two covered intersecting sets (the provider's, every addressless row in the fetch; the engine's, only the placeholders it had just added) and a sync therefore reported the same devices twice, in two different numbers. The engine is the layer that knows the outcome, so it took the whole disclosure, and `noAddressCount` and the `hasConsoleAddress` wrapper that fed it are gone — `mapEntry` now returns the device itself.

That warning's history is worth keeping, because both of its rewrites were about the same trap: a provider describing an outcome it does not decide. Builds up to 2.8.188 phrased it as *"N devices without a primary IP were skipped."*, which stopped being true the moment those devices became placeholders instead of being dropped; 2.8.189 corrected it to a pure observation about the fetch, and then it was the *duplication* that had to go. The endpoint-suppression rule it was entangled with is unchanged and still load-bearing: a row with a usable `primary_ip` and an **empty name** is emitted endpoint-less on purpose, because it cannot become a server, and the engine reports it under its own empty-name skip line (§4.12.1) — not as an addressless device, which it is not. The `hasConsoleEndpoint` predicate that once shared the definition of "has a console address" with the providers was **removed** along with that aggregate (`src/models/inventory.ts`): collapsing the warnings took its last caller, and a second implementation of the rule that nothing calls — kept in step by convention, with no test that would fail on divergence — is the drift it existed to prevent rather than a guard against it. `selectPrimaryEndpoint` (`syncEngine.ts`, via `selectSshEndpoint` then `selectTelnetEndpoint`) is now the **sole** definition: an `ssh` endpoint with a non-empty host, else a `telnet` one — which is why a BMC-only device correctly has an endpoint and no console address, the rule being keyed on the connectable kinds rather than on `endpoints.length`. A provider must not re-derive it, because the engine — not the provider — owns the addressless outcome.

#### 4.12.4 EVE-NG Inventory Source

A second built-in inventory provider (`src/services/inventory/providers/eveNgProvider.ts`, id `eve-ng`), registered beside NetBox in `activate()`. **Labs become folders; nodes become telnet servers.**

**Config fields**, in form order — the list is part of the provider fingerprint, so it is fixed:

| Field | Type | Notes |
| --- | --- | --- |
| `baseUrl` | string, required | The EVE-NG web UI address; a trailing slash is tolerated. Self-signed HTTPS is **not** supported (the extension host's fetch has no per-source trust store to relax) — use `http`, or a trusted certificate. |
| `username` | string, required | |
| `password` | password, required | Vault-stored (`SecretStorage`), never in settings. |
| `rootFolder` | string, optional | Subtree of the lab folder tree to scan. Defaults to `/`. |
| `filter` | string, optional | Case-insensitive substring matched against each lab's full path. Id + type deliberately match `SAVED_FILTER_TARGET_FIELD_ID`, so the shared saved-filter picker attaches to it. |
| `includeStopped` | boolean, **default true** | When off, stopped nodes are omitted — which makes them look deleted, so the source's prune policy applies to them. The default is expressed through `InventoryConfigField.defaultValue`. |
| `consoleHost` | string, optional | Override host for console connections when EVE-NG is behind NAT. |

**API surface.** All calls go through a module-private `EveApiClient`, so future Professional divergences land in one place. Login is `POST /api/auth/login` with `{username, password, html5: "-1"}` — the `html5: "-1"` is what makes EVE-NG report *native* `telnet://host:port` console URLs rather than browser HTML5 console links; without it every node maps to zero endpoints. undici's fetch keeps no cookie jar, so the `unetlab_session` cookie is captured from the login response and replayed as a `Cookie` header on every subsequent request. Every response is a JSend envelope (`{code, status, message, data}`) and is validated as such: a rejected password comes back as **HTTP 200 with `status: "fail"`**, which a status-code-only client would read as success.

**Crawl.** `GET /api/folders{path}` (each path segment percent-encoded — lab and folder names routinely contain spaces) is walked breadth-first from `rootFolder`, collecting `data.labs`; `GET /api/labs{labPath}/nodes` then fetches each surviving lab's nodes. That payload is an object keyed by node id, except for an empty lab, where EVE-NG returns an empty **array** — both are accepted, because failing the sync over one empty lab makes every other lab's servers look deleted. The walk **never leaves the `rootFolder` subtree**: server-supplied folder AND lab paths are boundary-checked (`isWithin`), and any path bearing a `.`/`..` segment is rejected before it is built into a request, so `new URL` cannot collapse it past the check onto a different origin path with the session cookie attached (an out-of-subtree lab is skipped with an aggregate warning). Two **hard caps** — 1 000 labs and 10 000 nodes — set `truncated` (which stops `computeSyncPlan` pruning the servers of labs the crawl never reached) and name what was dropped, as do the **depth cap** (12), the **request budget** (2 000 listings, warned exactly once), and a **wall-clock crawl deadline** (120 s, task #30). The deadline bounds *time* where the other caps bound *work*: a tree within every cap but served by a slow EVE-NG box could otherwise crawl for minutes and hang the sync/refresh. It is computed once per crawl and shared between the folder walk and the per-lab node fetch, so a source whose *lab count* — not its folder tree — blows the budget is bounded too; tripping it sets `truncated` and pushes a deadline-named warning **on the sync path**. The status path shares the budget and still has no warnings channel of its own, but it is no longer mute about it: a **manual** Refresh Lab Status now warns that the status shown is partial (§4.12.6). The poll stays quiet by design. The visited-set and dot-segment/`..` rejections do NOT set `truncated`, because they only refuse to follow a bad edge rather than abandon real labs. A folder or lab that **404s mid-walk** (deleted between the parent listing and its own fetch) is skipped with a warning rather than aborting the whole sync — except a 404 on the `rootFolder` itself, which is fatal (an empty result there would prune the entire inventory). Every request sends `redirect: "manual"`, so a 3xx from the lab box cannot carry the crawl (or the login POST body) to another origin; a redirect is a protocol error.

**Session expiry.** A mid-crawl 401/403 triggers exactly **one** silent re-login and one retry; a second failure surfaces as an `auth` error. EVE-NG expires sessions aggressively, so failing the first 401 loses syncs a single round trip would have saved — but retrying indefinitely turns a wrong password into an unbounded login loop.

**Mapping.**
- `externalId` = `` `${labPath}#${nodeId}` `` — every lab has a node `1`, so a bare node id would collapse them all into one server. **A LAB RENAME OR MOVE RE-IDENTIFIES EVERY NODE IN IT**, and that is a known limitation rather than a bug: the lab path is part of the identity, so changing it makes the old `externalId`s vanish from the fetch — the sync hands their servers to the source's Removed-Device Policy (moved to `_orphaned` under the default) while the nodes arrive as fresh adds, which loses the per-server hand edits and saved credentials on the old records. EVE-NG exposes no lab-stable GUID to key on, so there is nothing more durable available to identify with; the alternative (keying on node id alone) collapses labs into each other, which is worse. A node renamed WITHIN its lab keeps its identity and its `name` simply follows, as with any other provider. This is disclosed to users in the release notes and the README, since a lab reorganization done in good faith is a configuration-loss event.
- `name` = the node name, or `node-${id}` when blank. A node is **never dropped** for a cosmetic data problem: a device missing from the tree reads as deleted at the source.
- `folderPath` = the lab's own folder, made relative to `rootFolder`, plus the lab name (file minus `.unl`) as the final segment.
- `endpoints` = one `{kind: "telnet", host, port}` when `console === "telnet"` and `url` parses as `telnet://host:port` (see §4.4.4 for how the engine maps that onto a telnet server). The host is `consoleHost` when set; otherwise the URL's host, unless that is loopback or `0.0.0.0` — the usual answer, since EVE-NG is describing its own machine — in which case the `baseUrl` hostname is substituted. A non-telnet console, or none yet, yields `endpoints: []` and the device is still emitted. The provider says nothing further about it: **the sync's single addressless line (§4.12.2) is the only report**, covering both the nodes it has just made placeholders and those that already were. Up to 2.8.189 the provider also pushed its own aggregate (*"N nodes have no telnet console URL … were imported without a connection endpoint."*) beside the engine's line, so a plan carried two lines about intersecting sets of nodes; `noConsoleCount` and the `hasEndpoint` half of `mapNode`'s return went with it.
- **An HTML5/VNC-only node is NOT a "not yet" case.** The engine's line reads *"no console address **yet**"*, and that wording is deliberately provider-agnostic — the engine is handed no provider identity and must not prescribe an EVE-NG remedy (the same rule `addresslessUnavailableMessage` follows, §4.12.2). The "yet" is right for the common EVE-NG case, a **stopped** node, which gains a telnet console the moment it starts. It is not a promise. A node whose `console` is `vnc` (or any other HTML5 console type) **has** a working console — just not one this extension can drive, since Nexus connects to a node over telnet. Such a node is imported addressless and **stays** addressless: re-syncing will never give it an address, and nothing changes until its console type is changed to `telnet` in EVE-NG itself (or the node is rebuilt from a template whose console is telnet). Nor can the UI distinguish the two: `ServerConfig` persists the console ADDRESS but never the console TYPE the node would have needed, so a stopped node and a VNC-only one render identically in the tree and its tooltip. This is a documentation-level disclosure precisely because there is nowhere cheap and provider-agnostic to say it in the product.
- `attributes` / `attributeKeys` = `lab`, `template`, `type`, `console`, `status` (`running` for EVE-NG status 2, else `stopped`), `image`, `name`; empty values are omitted so a filter like `image=` cannot match every diskless node.

**`instanceKey`** is the canonical `scheme://host[:port]/path` of the base URL, mirroring `netboxInstanceKey`: it KEEPS any mount path, because the fetch does too (`http://gw/eve1` and `http://gw/eve2` are two distinct deployments behind one reverse proxy, and collapsing them would let one adopt the other's kept servers). A pasted `/api` suffix is stripped from both the key and the fetch string so it cannot double into `/api/api/...`. Userinfo, query and fragment are stripped — the key is persisted on every kept server and copied into backups.

**`testConnection`** logs in and probes `GET /api/status`, falling back to `GET /api/folders/` **only** on a 404 (an older build without the endpoint). An auth failure bubbles as-is and is never masked by a fallback that could succeed on a laxer endpoint.

**Edition.** `detectEdition` marks the server Professional when EITHER a string `data.edition` from `/api/status` contains `pro` (case-insensitive) OR the legacy `data.version` suffix does — some installs report the edition in the dedicated `data.edition` field while `data.version` is just a numeric build string, so a version-only check would miss them. It then appends exactly one warning per sync: *"EVE-NG Professional detected — Pro support is preliminary in this version; lab discovery and console mapping are validated against Community edition."* Community is the certified target. The check is defensive — an absent or non-string `edition` falls back to the version check, and a non-Pro `edition` string still resolves to Community. A missing `/api/status` is treated as *unknown* rather than fatal — edition detection is an optional capability probe.

#### 4.12.5 Inventory Sources in the Settings Tree

The Settings view's flat "Inventory Sources" link is an expandable group (`InventorySourcesGroupItem` / `InventorySourceItem`, `src/ui/settingsTreeProvider.ts`). Its children are one row per `NexusCore.getSnapshot().inventorySources` entry — label = the source name, description = `{provider label} — {last sync}` — followed by a trailing **Add Inventory Source…** row that is present even with zero sources. The two surfaces render the last-sync time DIFFERENTLY on purpose (both from `services/inventory/sourceDescription.ts`): the Settings tree row shows an ABSOLUTE `YYYY-MM-DD HH:MM` stamp via `sourceDescriptionAbsolute` (P2-1), because the tree only refreshes when a source record changes — a relative "synced N ago" there would freeze at whatever it first rendered — while the Manage Inventory Sources panel keeps the relative age via `sourceDescription` (it re-renders while visible, so the age stays current). "never synced" is shown by both when a source has never completed a sync.

Each row carries `contextValue` `nexus.inventorySource`, which the four `view/item/context` inline entries key on: Sync Now, Edit, Template Rules, Remove. Clicking a row edits it. The rows are provider-agnostic — built from the snapshot record plus the registry's label lookup, with no branch on `providerId` — and a provider the registry cannot resolve falls back to its raw id, so a source whose provider extension is missing stays visible and removable.

`SettingsTreeProvider` takes an optional `NexusCore` and `InventoryProviderRegistry` and refreshes on `core.onDidChange`, but ONLY when the inventory-source signature actually changes (MINOR-8) — a terminal or tunnel blink does not re-render the tree. It does not need a periodic refresh to keep the row labels accurate, because the row's last-sync stamp is absolute (`sourceDescriptionAbsolute`) rather than a relative age; a source edit or a new sync is exactly what changes the signature and re-renders. Subscriptions are released on dispose. `nexus.inventory.manage` is unchanged and remains the palette route in.

#### 4.12.6 Live lab status (running-lab highlight)

EVE-NG sources can show which labs are **running**, live, on the Command Center tree. This is an EVE-NG-only affordance: it is driven by an optional provider capability, `InventoryProvider.fetchStatus`, that only the EVE-NG provider implements — NetBox (or any provider without it) simply shows no status.

- **Refresh Lab Status** (`nexus.inventory.refreshStatus`) fetches every source's running/stopped state and applies it. It reuses the same login / folder-walk / node-fetch machinery `fetchInventory` does, but emits only status — no `includeStopped` filter (all nodes are reported; the tree decides what to show) and a fresh telnet console endpoint only for running nodes (parsed through the same helper the sync mapper uses, with the same loopback/`consoleHost` substitution). Applying the report is a two-step: `applyInventoryStatus` updates only NexusCore's runtime `serverStatus` map (no persistence), then **`healSyncedConsolePorts`** persists a **telnet console-port reassignment** onto the owned server (task #29 / D8) — but only for a running, telnet, non-addressless, **sync-owned** node whose reported console host/port differs from the persisted one, so a **hand-edited** port is never touched. When it heals, it advances the `syncedHost`/`syncedPort` stamp with the value and batches all of a source's heals into one write; an already-open telnet terminal keeps its port, since the heal affects only the *next* connect. It skips providers with no `fetchStatus`, is non-fatal per source (one flaky lab box never aborts the sweep, and the heal is non-fatal on top of that), and respects the per-source busy-guard so it never races an in-flight sync/edit/remove. Available from the palette and as a Command Center title action.
- **Bounded like a sync, and it says so on a manual refresh.** The refresh runs the same crawl caps and the same 120 s wall-clock deadline as `fetchInventory` (§4.12.4), so a huge or slow lab tree bounds a refresh too. `InventoryStatusReport` carries only `statuses` and `truncated` — there is no warnings channel — but `refreshStatus` now reads the flag and, on the **manual** invocation only, shows one warning after the sweep naming the affected source(s): the lab crawl hit its time budget, the status shown is partial, some nodes may be stale or still unknown, and the remedy is to narrow the source's **Root Folder** / **Lab Filter** or simply run it again. One message per sweep, never one per source, and the **poll path stays silent by design** — it fires on a timer, and a warning per tick would nag about a lab that is merely large. This follows the same manual-only rule as the total-failure warning below; the two cannot both fire for one sweep, since a truncated report *is* a report and so counts as a success. The flag is collected where the report is **applied**, so a sweep superseded by a newer one warns about nothing: its results never reached the tree.

  What is still open is the *rendering*: `applyInventoryStatus` MERGES a truncated report (retaining prior status for absent entries instead of clearing them), which is the correct fail-safe — an unreached node must not read as removed — but it leaves that node showing its last known, possibly stale, state, or `unknown` if it never had one, and the tree row and tooltip cannot tell that apart from a state confirmed a second ago. A user reading a stale `(stopped)` on a node that is now running is now told the *refresh* was partial, but not *which* nodes went unconfirmed. Distinguishing "stale, not refreshed this pass" from a freshly-confirmed state per node (**KNOWN GAP**) needs a per-node freshness marker and is deliberately still open.
- **The poll.** `nexus.inventory.statusPollSeconds` (a new **Inventory** settings category, default **0 = off**, range 0–3600) fires Refresh Lab Status every N seconds, but ONLY while the Command Center view is visible AND the interval is > 0 — there is no point refreshing a highlight nobody is looking at, and no reason to keep hitting a lab box while the panel is closed. The timer seeds from the view's current visibility (VS Code does not fire the visibility event at registration), re-arms/stops when the interval setting changes, and is disposed with the extension.
- **What you see.** A running node's server row shows a **green filled dot** and a `(running)` suffix; a stopped EVE node shows a **hollow dim dot** and an explicit `(stopped)` suffix; a non-EVE (no-status) server is unchanged. Stopped-ness is stated rather than implied because it is the premise for **Start Node** (§4.12.7) — the worst case, connected + stopped, would otherwise render a green plug, no state text, and a Start Node menu: a row contradicting its own menu. Both suffixes ride the row's description, so they follow `nexus.ui.showTreeDescriptions`.
- **The ▶ badge.** A green **▶** (tooltip `Running`) is painted by a `FileDecorationProvider` (`src/ui/inventoryStatusDecorationProvider.ts`) matching a `nexus-status:` resourceUri the tree stamps on server and folder rows — on **every running node's own row**, and on **any folder that directly contains at least one running node** (a node's lab folder is its own `group`, read exactly as the tree assigns membership, so an EVE-NG lab lights up from its running nodes; a hidden running node lights nothing, matching the tree's own `!isHidden` rule). The row badge is load-bearing, not decoration: a CONNECTED server always keeps its plug icon (the connected affordance must not be lost to a status indicator) and so never shows the running dot, which makes `▶` plus the `(running)` suffix the only running indicator there. Decoration lookups are O(1) Set hits derived once per snapshot, and the change event fires only when the running sets actually change.
- **Scope and lifetime.** Status is runtime-only — it is never persisted and re-fetched on demand or by the poll — and scoped strictly by source (a status maps onto a server only when that server exists and is owned by the reporting source), so one lab's refresh can never overwrite another's highlight.

**BMC menu gating (task #27).** The two BMC actions — **Connect BMC Serial Console** (`nexus.server.connectBmcSol`) and **Open BMC Web Console** (`nexus.server.openBmcWebConsole`) — are now shown only on a server that actually has an `ipmiHost`. A server with a non-blank `ipmiHost` gets an `.ipmi` marker appended to its tree `contextValue` (`nexus.server.ipmi` / `nexus.serverConnected.ipmi`); the two BMC entries require `/^nexus\.server(Connected)?\.ipmi(\.eveRunning|\.eveStopped)?$/` (the trailing optional group is the node-control marker below), while every other server menu was broadened with an optional `(\.ipmi)?` so a BMC server keeps all its ordinary actions. Addressless-with-BMC servers correctly still show the BMC actions.

#### 4.12.7 Node control (Start / Stop an EVE-NG node)

An EVE-NG lab node can be **started or stopped straight from its Command Center row**, so a node that is down can be brought up without leaving the editor. This is EVE-NG-only, driven by a second optional provider capability, `InventoryProvider.controlNode(config, secrets, externalId, action)`, that only the EVE-NG provider implements.

- **Start Node** (`nexus.inventory.startNode`) and **Stop Node** (`nexus.inventory.stopNode`) act on the server the tree row names. They resolve the server's inventory source and its provider, and dispatch through `controlProviderNode` — the mutating twin of the status wrapper. Unlike the status refresh, which degrades every flaky-lab error to "no update" so a background poll can never nag, `controlProviderNode` **propagates** a failure: a start/stop the user issued that did not happen surfaces as an error naming the node. On success it shows a brief *"Starting/Stopping …"* and fires a best-effort **Refresh Lab Status** for that source; because the node boots over several seconds, the highlight lags the command by a poll or two — that is expected, not a bug.
- **Edition awareness.** **Community is the certified path** — start/stop is `GET /api/labs{labPath}/nodes/{nodeId}/{start|stop}`, validated against the JSend envelope like every other EVE-NG call. **Professional is edition-aware but PRELIMINARY** (uncertified): it uses the edition-aware evengsdk verbs — a `PUT` to the node-action endpoint, with `stopmode: 3` on stop — and is certified later against a real Pro instance (Phase 3). An *unknown* edition (an older build with no `/api/status`) is treated as Community best-effort rather than refused. Only single-node start/stop is supported this phase (no lab-wide start/stop, no destructive node wipe).
- **When the actions appear.** The Start/Stop entries are gated by **origin and state**: the tree stamps an `.eveRunning` / `.eveStopped` marker onto a server's `contextValue` (in the fixed order `nexus.server[Connected][.ipmi][.eveRunning|.eveStopped]`) **only** for an EVE-origin server whose running/stopped state is already known. A freshly-synced EVE node with no status yet, and any non-EVE server, carry no marker — so you run **Refresh Lab Status** first and the extension never offers an action blind. **Start Node** shows only on a stopped node (`…\.eveStopped`), **Stop Node** only on a running one (`…\.eveRunning`). Adding the marker meant broadening every anchored server-menu `when` regex to tolerate the optional eve group first, so an EVE node keeps all of its ordinary context actions.
- **The row says which state it is in.** Every EVE-origin node's tooltip carries a labelled `Lab status:` line — `running`, `stopped`, or `unknown — run Refresh Lab Status` — matching the tooltip's other labelled-line entries (`IPMI/BMC:`, `Template-applied:`, `Synced from …`). It exists specifically to explain an ABSENT Start/Stop: the state gate above is invisible in a context menu, so the row itself names the state and, in the unknown case, the command that resolves it. A non-EVE server gets no such line.
- **Where the actions appear.** Both entries sit in their own `00_power` menu group, above the connect actions, and are also offered by the row-click **Profile Actions** quick pick (which reads the state back off the same `contextValue` marker rather than re-resolving it, so the two surfaces cannot disagree). Neither is in the Command Palette (`commandPalette` `when: false`) — they only mean anything against a specific node, so a palette search for "Start Node" finds nothing.

## 9. Scripts

Author-and-run automation on top of any active SSH, Serial, or Local Shell session.

### 9.1 Flow
1. Create a `.js` file under `<workspaceRoot>/<nexus.scripts.path>` (default `.nexus/scripts/`). Tag the leading JSDoc block with `@nexus-script` and any of the optional fields `@name`, `@description`, `@target-type`, `@target-profile`, `@default-timeout`, `@lock-input`, `@allow-macros`.
2. First time a Nexus script command runs in the workspace, `ScriptTypesGenerator` seeds `types/nexus-scripts.d.ts` + `jsconfig.json` so the editor gives autocomplete and JSDoc hovers for `expect`, `sendLine`, `poll`, `prompt`, etc.
3. Invoke `nexus.script.run` from the Command Palette / sidebar / `▶ Run in Nexus` CodeLens. The runtime parses the header, resolves the target session (filter by `@target-type` values `ssh`, `telnet`, `serial`, or `local`; auto-select on `@target-profile` id/name match; else QuickPick), and spawns a `node:worker_threads` Worker.
4. While running, the script's status shows in the **Nexus Scripts** status-bar entry and the **Nexus Scripts** Output Channel logs timestamped events (`→ expect …`, `← matched`, `log info: …`, `end: completed (…ms)`).

#### 9.1.1 Script Templates
- `Nexus: New Nexus Script` opens a starter-template picker before asking for the script name.
- Built-in templates are **Basic command**, **Wait for prompt then send**, **Capture command output**, and **Backup running config**.
- New scripts are written to the resolved scripts directory: `<workspace>/<nexus.scripts.path>` when a workspace folder is open, or the extension global-storage scripts directory when no folder is open.
- If `<name>.js` already exists, Nexus opens the existing file instead of overwriting it.
- Template bodies include the required `@nexus-script` marker and use the entered script name in the generated `@name` field.
- The generated script comments link developers to `types/nexus-scripts.d.ts`; that type file is seeded on first script command run in the workspace.

### 9.2 Macro coordination
- When a script starts, macros on the script's bound session are suspended by default (`nexus.scripts.macroPolicy = "suspend-all"`). Macros on unrelated sessions keep firing.
- `@allow-macros name1, name2` in the header whitelists specific macros.
- Inside the script: `macros.allow("pw")`, `macros.deny("pw")`, `macros.disableAll()`, `macros.restore()` mutate the active policy for the rest of the run. The original policy restores on any exit path.

### 9.3 Stopping / failure paths
- User stops from the status bar, CodeLens, or `nexus.script.stop`. `worker.terminate()` kills tight loops in <100 ms.
- Wait timeout: `expect` throws `{ code: "Timeout", pattern, timeoutMs, elapsedMs }`; `waitFor` returns `null`.
- SSH drop / serial session close / Local Shell unregister while a wait is pending: pending RPCs reject with `{ code: "ConnectionLost", sessionId }`; the runtime gives the script a 150 ms grace period to run `try/catch`/`finally` before force-termination.
- Macros, input lock, and output-observer subscription are restored/disposed on every exit path (`finally` in `cleanupRun`).

### 9.4 Isolation
- The Worker has its own V8 isolate with `resourceLimits.maxOldGenerationSizeMb = 192` so a runaway allocation terminates the worker rather than bloating the extension host.
- The Worker bundle (`dist/services/scripts/scriptWorker.js`) does NOT import `vscode`. All UI operations round-trip through the main thread via structured-clone `postMessage`.

### 9.5 Script folders
- Scripts are organized on the filesystem, not by metadata — a folder in the Scripts sidebar is a real directory under the resolved `nexus.scripts.path`. `src/services/scripts/scriptScanner.ts` (`scanScriptsDir()`) is the single recursive bounded scan, called independently by both `ScriptTreeProvider` (`src/ui/scriptTreeProvider.ts`) and `pickScriptFromWorkspace()` (`src/services/scripts/scriptPicker.ts`, backing **Connect and Run Script…** from server, serial, and Local Shell profile items) — a shared function, not a shared cache, so the picker works correctly even before the Scripts view has ever been revealed, and is never stale behind the tree's debounce.
- **Scan bounds** (`SCRIPT_SCAN_MAX_DEPTH = 10`, `SCRIPT_SCAN_MAX_ENTRIES = 500` in `scriptScanner.ts`): the scanner descends into directories up to 10 levels deep, so a folder at exactly the maximum depth `normalizeFolderPath` lets you create is still fully read for its own scripts and subfolders; a folder found one level beyond that (11) still renders in the tree but is never descended into — it expands to no children. The entry budget counts every directory and every file examined, `.js` files included, so a directory holding thousands of scripts is bounded the same way as one full of unrelated files — once exceeded, the scan stops (reporting exactly 500 examined, never one past it) and a truncation node is pinned first at the root of the tree (its click action opens the `nexus.scripts.path` setting). Dot-directories and `node_modules` are skipped case-insensitively (relevant on WSL2's case-insensitive `/mnt/c`); `.js` matching is likewise case-insensitive. The generated `<scriptsDir>/types/` directory is skipped only at the scripts root, and that check is case-insensitive too — a user's own `cisco/types/probe.js` is a normal, scanned folder. Directory-type detection uses a bitmask test (`type & vscode.FileType.Directory`, not strict equality), so a symlinked directory (an NTFS junction surfaced through WSL2, for example) is followed as a folder rather than silently dropped; the depth and entry caps are what bound the cost of a symlink cycle, not a separate symlink check. Following a link is a promise the scanner can keep and the file-system watcher cannot — VS Code's recursive watcher resolves only its own root and exposes no follow-symlinks option — so every folder at or below a link is flagged (`ScannedFolder.linked`, inherited downward) and rendered with a `file-symlink-directory` icon and a tooltip stating that changes inside it are not detected automatically and that Refresh will pick them up. The alternative (a second watcher rooted at each linked folder) is rejected in a comment at `ScriptTreeProvider.ensureWatcher()`: it is unverifiable under a mocked `vscode`, it can only be installed one render behind the scan that discovers the links, and a watcher believed to work but silently not working would remove the user's reason to Refresh. `pickScriptFromWorkspace` is unaffected — it rescans on every invocation and never serves a cache. `SCRIPT_SCAN_MAX_DEPTH` is imported from `MAX_FOLDER_DEPTH` rather than re-declared — it is the same bound seen from both sides (what `normalizeFolderPath` lets you create, and what the scanner has to find). The skip list is exported from the same module as `findHiddenScriptFolderSegment()` and reused by the **New Folder** / **New Script** validators, so a name the tree would never render is rejected at the prompt instead of being created on disk as an invisible directory that then reports "already exists". Truncation is announced in **Connect and Run Script…** as well as the tree: `pickScriptFromWorkspace` appends the reason (entry cap or depth cap) to its quick-pick placeholder, or to the "no scripts" message when a truncated scan matched nothing — the case that previously produced the misleading bare "No Nexus scripts compatible with SSH profiles".
- `ScriptTreeProvider.getChildren()` is hierarchical: folders render before scripts, both alphabetically (natural compare) — this is a straight filesystem listing, so unlike macro order it carries no user intent to preserve. A folder renders whether or not it contains a script, and whether or not it's empty, so long as it isn't in the skip list. The three-link onboarding placeholder (New Script / Open Scripting Guide / Open Script Examples) renders only when there is no `@nexus-script`-marked file anywhere in the tree, and only at the root.
- **Scan generation counter**: each `refresh()` bumps a generation counter and starts a new scan; `getChildren()` awaits the scan tied to the CURRENT generation, looping to pick up a newer scan if a fresher one started while the awaited one was still in flight, rather than ever rendering a stale directory's contents (guards against, e.g., the user changing `nexus.scripts.path` while an old, slow scan of the previous directory is still resolving).
- The file watcher binds to `**/*` (not `**/*.js`) precisely so a directory-level rename or delete event fires at all — a directory event carries the directory's own path, which structurally can never match a `*.js` glob. Watcher events are coalesced through `src/utils/coalescedInvoker.ts` with a ~300ms debounce so a burst of saves, or a directory rename, triggers exactly one rescan; `nexus.script.refresh` (view title bar `$(refresh)` button) bypasses the debounce for an immediate manual rescan.
- **Moving a script between folders** is a drag: drag a script row onto a folder row to move it there, onto another script to move it into that script's folder, or onto empty space (or any of the truncation / scanning / onboarding rows, which all sit at the root) to move it back to the root. Because a script folder is a real directory, this is a filesystem rename rather than a metadata edit — it goes through a `WorkspaceEdit`, so an editor already open on the script follows it and the move joins the undo stack. Three cases refuse and say why rather than guessing: a **running** script (`ScriptRuntimeManager` keys a run by its script's path, and so does the Stop action on a tree row, so moving it would leave the run keyed to a path nothing renders — no badge, no Stop, still running), a **name collision** in the target folder (never overwrite user source code), and a source outside the scripts root. Dropping a script into the folder it is already in is a silent no-op. Only scripts are draggable — a folder is a directory, and dragging one would move a whole subtree. The view deliberately does not enable `canSelectMany`: it would let a drag carry several scripts, but it also changes what every existing script context command receives, and Run / Stop / Delete / Edit each act on one row. What crosses the `DataTransfer` is a lookup token and nothing else — the dragged URI stays host-side in `ScriptTreeProvider.lastDragCapture` and is cleared by the drop it belongs to, because this drop ends in `applyEdit(renameFile)` and a payload naming a path would be an instruction to move that path, writable by anything that can write this MIME. Added in 2.8.77; 2.8.75 shipped script folders with no way to put an existing script into one from the sidebar at all.
- **Open Scripts Folder** opens the scripts directory itself via `env.openExternal`, falling back to `revealFileInOS` only if that reports failure (a `file:` URI from a remote window resolves on the local machine) and to a message naming the path if neither works. The order matters and was wrong until 2.8.77: `revealFileInOS` is Electron's `showItemInFolder`, which reveals its argument *inside the containing folder*, so handed a directory it opens that directory's **parent** — `<workspace>/.nexus` for the default `.nexus/scripts`, or the extension's global-storage directory for the no-workspace fallback. Neither holds a script, and the command is called Open Scripts Folder.
- **New Script** (`nexus.script.new`) accepts a `/`-separated path (e.g. `cisco/backup`) and creates any missing intermediate directories. **New Folder** (`nexus.script.newFolder`, view title bar or a folder's right-click menu) creates a real, empty directory; naming one that already exists is a no-op with an info message. Both commands, invoked from a folder's context menu, pre-seed that folder as a `folder/` prefix in the input box. A folder's context menu also offers **Reveal in Explorer**.
- **Path validation** reuses the same folder-path grammar as macros and the Connectivity Hub (`src/utils/folderPaths.ts`: `normalizeFolderPath`, `MAX_FOLDER_DEPTH = 10`) for the directory portion of a New Script / New Folder path, and the pre-existing `/^[A-Za-z0-9._-]+$/` regex for the leaf script name. The two are validated separately and deliberately: the leaf regex alone would accept `..` as a whole segment (safe only because the pre-folders implementation forbade `/` entirely), so once `/` is allowed the directory segments must go through `normalizeFolderPath` — which rejects `.`, `..`, and depth beyond 10 — or a name like `../../../../home/you/startup` would resolve outside the scripts directory via `Uri.joinPath`. A `\` in the input is rejected outright with a message telling the user to use `/`.
